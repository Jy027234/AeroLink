# D14 采购承诺与销售结算实施设计

日期：2026-09-09。本文记录基于当前代码和 D14 待办的设计及阶段进展，不代表 D14 完整验收。

## 当前实施进展与已确定的口径

- 新增采购覆盖量、采购审批快照和结算金额纯函数；连同能力权限 4 个测试文件 / 40 项定向验证通过。尚未接入采购 API 或实际结算业务，不能据此标记采购或财务流程完成。
- 采购承诺头限定同一客户订单和同一供应商，使用独立 `commitmentNumber`。首个数据库增量采用 `DRAFT/PENDING_APPROVAL/APPROVED/CONFIRMED/CLOSED/REJECTED/CANCELLED`，没有实际发送事实就不记录 `SENT`。
- `receivedQuantity` 仅表示已经验收、可进入分配的收货量；待检、仅到货及拒收必须由后续独立收货事实表示。来源链必须保存具体采购行、收货行、库存明细及 INBOUND 的 ID，不能按件号或数量回推。
- 同一销售行的覆盖量为“非采购库存分配减释放”加“采购承诺减取消”。采购来源库存的分配和出库不能再加一遍覆盖量；取消与已验收收货、直发合计不得超过承诺量。
- 首个数据库增量的 `directShippedQuantity` 固定为 0。完整 D14 仍须实现独立受控直发来源、适用质量审核及 D13 交付证据链，再通过向前迁移开放，不以此临时阻断代替 D14 的最终要求。
- 结算按应收、应付分别计算 `PAYMENT/CREDIT/REFUND/REVERSAL`。冲销引用一条原事件并保留原记录；不直接再次冲销冲销记录。已付款后的信用冲减可以形成待退金额，不能自动生成实际退款或总账事实。

## 1. 首期边界与结论

D14 只覆盖公司自有库存销售和背靠背采购转售，交易币种固定为 USD。采购承诺是公司对供应商的采购事实，客户 PO、客户订单和客户应收是另一条销售事实；两个编号、金额、权限和附件不能共用一列或互相推导。采购承诺先覆盖供应商、关联销售行、成本、交期、供应商确认、收货/直发证据；结算只保存外部财务凭证摘要和可核对的收付款、冲销，不建设总账、付款网关、税务引擎或多币种。

金额审批沿用已经落地的 USD 分级规则：总额 `<= 5,000` 需要 MANAGER，`> 5,000 && <= 50,000` 需要 FINANCE，`> 50,000` 需要 GM；创建人不能审批自己的采购承诺。AOG 不绕过金额级别。现有策略把系统管理员和商业审批权分开，`admin` 不能仅因拥有全能力替代 GM；采购承诺应复用同一显式审批判断。

供应商直发在当前系统仍是关闭状态。D14 可以先定义其数据和受控接口，但在 D05 适用质量审核、证据版本和履约状态链路完成前，`SUPPLIER_DIRECT` 只能停留在待核/阻断状态，不能因为没有库存流水而直接标记 SHIPPED、DELIVERED 或完成结算。

## 2. 当前可复用模型和入口

| 事实 | 当前模型/入口 | 可复用内容 | 不能直接当作 |
| --- | --- | --- | --- |
| 需求和供应商报价 | `RFQ`、`RfqLine`、`Inquiry`、`InquiryItem`、`SupplierQuote`；`/api/supplier-quotes` | RFQ 行 ID、供应商 ID、件号/数量、`unitPriceDecimal`、`currency`、`validUntil`、询价来源 | 公司已经承诺采购；供应商报价可被撤回、过期或币种待核 |
| 客户商业承诺 | `Quotation`、`QuotationLine`；`/api/quotations` | 客户报价行、来源供应商报价快照、USD Decimal 金额、审批快照、商业版次 | 供应商 PO 或采购应付；客户报价成本不能在销售响应中绕过 `view_cost` |
| 客户成交和履约需求 | `Order`、`OrderLine`；`/api/orders`、报价 `/:id/accept` | 成交行、客户、订单版本、交付量、客户 PO 兼容字段 | 供应商承诺。当前 `Order.poNumber` 和 `Order.poNumberCustomer` 都按客户采购单语义使用，不能写入供应商 PO |
| 自有库存分配 | `InventoryAllocation`、`AllocationAssignment`、`InventoryTransaction`；`/api/inventory-allocations` | 明确库存来源、父/子分配、数量守恒、Serializable、CAS、幂等、D12 逐行履约 | 采购承诺或付款；供应商直发不能伪造 OWN OUTBOUND |
| 质量和交付证据 | `FulfillmentReview`、`Shipment`、`ShipmentLine`、`ReturnHold`；`/api/shipments` | 实物身份、证书、寿命、附件版本/哈希、质量独立审批、签收/退货事实 | “供应商已确认”本身；D13 发运要求真实 OUTBOUND 和绑定质量复核 |
| 付款条款资料 | `Customer.paymentTerms`、`Supplier.paymentTerms` | 创建结算摘要时的候选条款快照 | 已生效的应收/应付凭证；当前字段是自由文本，不能自动推导已收/已付 |
| 金额一致性 | `moneyReconciliation.ts` 及各实体 Decimal shadow | 校验 Float 兼容字段与 Decimal 的一致性 | 应收应付明细或总账；它不记录支付、冲销和外部凭证 |

当前入口均经过认证和能力策略：`/api/supplier-quotes` 使用 `supplier_quote.read/create/update`，报价和订单分别使用 `quotation.*`、`order.*`，D12 分配使用 `inventory.manage` 并按当前报价/订单行校验归属，质量审核使用 `quality_review.read/approve`。`/api/purchase-commitments` 和 `/api/settlements` 目前不存在，不能把供应商报价的 `isWinner` 或客户订单的 `poNumber` 当作它们的替代入口。

供应商报价创建和中选已经要求精确 RFQ 行、供应商关系、USD 核实和未过期；多行 RFQ 不按件号猜测。D14 创建承诺时应从数据库重新读取这些关系并保存快照，不能信任客户端再次提交的件号、成本或供应商。

## 3. D14 第一批逻辑模型

以下是迁移设计，字段名用于确定契约，当前不落 schema。每个数量使用正整数，每个金额使用 `Decimal(18,4)`，所有金额行和头记录都写 `currency = 'USD'`；金额由服务端按行求和，客户端合计只用于展示。

### 3.1 `PurchaseCommitment` 采购承诺头

建议字段：

- `id`、唯一 `commitmentNumber`（AeroLink 内部采购承诺号）、`supplierId`；另有可空 `supplierReferenceNo` 保存供应商给出的 PO/确认号，唯一性至少限制在同一供应商内。
- `orderId` 必填，第一批限制一张承诺只对应一张客户订单；`quotationId` 从订单反查并保存以便审计。跨订单合并采购留到后续，不用隐含多对多关系。
- `fulfillmentMode`：`BACK_TO_BACK` 或 `SUPPLIER_DIRECT`。自有库存销售不创建采购承诺。
- `currency` 固定 `USD`、`totalCostDecimal`、`expectedDeliveryDate`、`paymentTermsSnapshot`、`supplierSnapshot`。条款和供应商名称必须是创建/确认时的快照，不能依赖后续修改的供应商资料。
- `status`：`DRAFT`、`PENDING_APPROVAL`、`APPROVED`、`SENT`、`CONFIRMED`、`PARTIALLY_RECEIVED`、`COMPLETED`、`REJECTED`、`CANCELLED`；`version`、`createdById`、`submittedById`、`approvedById`、时间戳及拒绝/取消原因。
- `approvalLevel`、`approvalPolicyVersion`、`approvalSnapshot` 保存金额、币种、供应商、全部行和交期的不可变审批证据；审批后价格、供应商和承诺数量不能原地改写。

### 3.2 `PurchaseCommitmentLine` 采购承诺行

每一行必须显式绑定当前成交事实：

- `purchaseCommitmentId`、`lineNo`、`orderLineId`、`quotationLineId`、`rfqLineId`。服务端要求三者关系为 `OrderLine -> QuotationLine -> RfqLine`，并核对当前订单行件号/数量；不接受只有 `partNumber` 的行。
- `sourceSupplierQuoteId` 可用于 `SUPPLIER_QUOTE` 成本来源；若人工成本确有必要，使用 `MANUAL` 加必填原因和证据，不允许伪造供应商报价 ID。供应商报价必须属于同一 RFQ 行、同一供应商、USD 已核实、未过期且数量足够。
- 服务端从来源和关联行生成 `partNumber`、`uom`、`quantityCommitted`、`unitCostDecimal`、`lineTotalDecimal`、`currency`、`sourceSnapshot`；客户端传入的同名字段只作校验，不能成为事实。承诺数量不得超过该订单行尚未被其他活动采购承诺覆盖的数量。
- `promisedDate`、`receivedQuantity`、`directShippedQuantity`、`status` 和 `version`。接收/直发量为派生或事务投影，不能用普通 PATCH 直接增加。
- 可存 `serialNumber`/`batchNumber` 作为供应商已明确的预期身份，但实际身份必须在收货或直发质量证据中重新核对；不能用预期值代替实物事实。

建议数据库约束包括 `(purchaseCommitmentId,lineNo)` 唯一、`orderLineId` 索引、正整数数量、USD 检查、Decimal 头行合计检查，以及限制承诺行的订单、报价、RFQ 行关系。多个承诺允许拆分同一订单行，但活动承诺总量不能超过订单行成交量；释放/取消只减少活动覆盖量并追加事件，不删除审计记录。

### 3.3 确认、收货和直发证据

采用追加记录而非覆盖头部字段：

- `PurchaseCommitmentConfirmation`：承诺 ID、确认类型、确认时间、内部记录人、供应商参考号、逐行确认数量/交期、证据对象 ID、证据版本和哈希、备注。供应商确认可以改变交期或确认量，但不能静默改变已审批价格、供应商和销售关联行；实质变更建立新承诺或显式修订。
- 手工收货不另写一套库存数量逻辑。D14 接口只负责校验承诺行、来源和数量，然后在同一事务调用现有库存服务的 `createInventoryAggregate`/入库事务路径，写 `INBOUND`、前后数量和承诺来源参考。收货后的公司库存仍是 D12 可履约的 `OWN`，采购来源是额外 provenance，不能新增一个绕过 D12 的“供应商库存”快捷路径。
- 收货提交证书、批次/序号、状态、寿命和附件；适用的 D05 质量审核不通过时只留下待检/阻断事实，不增加可履约数量。收到的库存随后仍需 D12 `reserve -> assign -> quality review -> consume`，D13 再管理实际发运和签收。
- `SUPPLIER_DIRECT` 不创建虚假的本地 `INBOUND` 或 `OUTBOUND`。第一批应保存供应商直发单、运单/签收和适用质量证据，逐行绑定订单和采购承诺；质量审核、附件版本和签收完成前不能将订单标记完成。当前 D13 的真实 OUTBOUND 发运入口不能直接承接直发，因此直发命令应默认返回“流程未开放”或进入人工待核状态，直到专用 D05 适配器验收通过。

### 3.4 应收/应付摘要和外部凭证

建议使用一对可核对的摘要和追加分录，而不是在订单或采购承诺上添加可任意修改的 `paidAmount`：

`SettlementSummary`：

- `id`、`direction`（`RECEIVABLE`/`PAYABLE`）、`referenceType`（`ORDER`/`PURCHASE_COMMITMENT`）、`referenceId`；引用必须由服务端解析，不能让客户把订单 ID 和采购承诺方向互换。
- `amountDecimal`、`currency = USD`、`dueDate`、`paymentTermsSnapshot`、`externalSystem`、必填 `externalDocumentId`、外部状态、`version`、创建/最后核对时间。
- `paidOrReceivedDecimal`、`offsetDecimal`、`outstandingDecimal` 均由分录投影计算并返回；第一批不允许客户端直接写这些派生值。应收按客户订单成交行金额， 应付按采购承诺行金额，不能用报价头部旧金额。

`SettlementEntry`：

- `summaryId`、`entryType`（`PAYMENT`/`OFFSET`/`REVERSAL`）、正数金额、外部凭证号、发生时间、原因、`reversesEntryId`（冲销时必填）和创建人；记录快照哈希并追加不可变审计事件。
- 同一外部凭证和同一幂等键不能重复入账；不能为负数、超过可冲销余额或跨方向套用。冲销不能删除原付款，必须追加反向分录并保留原凭证关系。
- AeroLink 只保存摘要/外部引用和对账结果，不写总账分录、不发起银行付款、不伪造“已收/已付”。若外部凭证缺失，摘要状态只能是 `PENDING_EXTERNAL_REFERENCE`，不能显示为已结清。

客户账期从 `Customer.paymentTerms` 复制为快照；供应商账期从 `Supplier.paymentTerms` 复制为快照。两者目前是自由文本，所以第一批的 `dueDate` 必须显式提供并由财务确认，不能在服务端猜测“Net 30”等文本的日期。

## 4. 权限、范围和响应投影

当前能力表没有 `purchase_commitment` 或 `settlement` 资源，实施时应先在 `capabilityPolicy` 集中增加窄资源，不用把新权限伪装成 `supplier_quote.manage` 或 `order.update`。建议能力键如下：

| 角色/范围 | 采购承诺 | 结算摘要 | 履约/质量 | 对外响应 |
| --- | --- | --- | --- | --- |
| Sales | 关联自己/部门订单的只读状态、确认交期和欠货量；不能读单位成本、供应商付款条款、应付 | 只能读自己订单的应收状态和欠款汇总 | 不获得库存分配或质量审批 | 成本、供应商凭证和 AP 全部隐藏 |
| Manager/采购 | `read/create/update/submit/confirm`，按订单当前 owner/department 范围；可录入采购承诺 | 只读或按业务授权查看关联摘要 | 收货继续用 `inventory.manage` | 成本按 `purchase_commitment.view_cost` 单独投影 |
| Finance | 全范围 `read/view_cost/reconcile`，承担财务级审批 | `create/update-entry/reconcile/export` | 可读订单事实，不替代质量审批 | 可看应收应付金额和外部凭证，不修改库存事实 |
| Quality manager | 只读与当前订单关联的交付、证书、直发/收货质量证据；不要求 `quotation.read` | 无 AP 成本权限 | `quality_review.read/approve`，独立于收货人/采购创建人 | 只返回质量安全字段和证据版本 |
| Operator | 只有显式授予的收货能力；不能创建或审批采购承诺 | 无 | 继续受 `inventory.manage`/质量规则约束 | 不返回价格和结算金额 |
| GM/admin | 可访问范围由现有策略决定 | 可运维/审计 | 仍须通过业务审批级别和禁自批校验 | admin 不因全能力自动成为 GM 审批人 |

每次读取和写入都从当前数据库关系解析范围：`PurchaseCommitment -> Order -> Quotation.createdBy/creator.department`，再调用 `assertCapability`。不使用创建时客户端传入的 owner，不因持有供应商报价 ID 绕过订单范围。财务全范围读取也要经过独立 capability；销售看到的订单详情不能通过嵌套采购行、结算摘要、审批快照或幂等重放泄漏成本。

采购承诺和结算事件只带业务 ID、状态、数量和非敏感变更提示；socket/outbox payload 不放单位成本、付款条款、外部凭证内容或客户价。PDF、CSV 和详情遵循同一响应投影。

## 5. 第一批接口契约

所有新增写操作必须带 `Idempotency-Key`、使用当前对象 `version` 做 CAS，并在 Serializable 事务中同时写业务事实、事件和 outbox。重放前重新检查当前权限；同键不同请求返回冲突。

### 5.1 采购承诺

```text
POST /api/purchase-commitments
GET  /api/purchase-commitments?orderId=&supplierId=&status=
GET  /api/purchase-commitments/:id
POST /api/purchase-commitments/:id/submit
POST /api/purchase-commitments/:id/approve
POST /api/purchase-commitments/:id/reject
POST /api/purchase-commitments/:id/confirm
POST /api/purchase-commitments/:id/receipts
POST /api/purchase-commitments/:id/direct-ship-evidence
```

创建请求的最小事实应为：

```json
{
  "orderId": "order-id",
  "supplierId": "supplier-id",
  "fulfillmentMode": "BACK_TO_BACK",
  "currency": "USD",
  "lines": [
    {
      "orderLineId": "order-line-id",
      "source": { "type": "SUPPLIER_QUOTE", "supplierQuoteId": "supplier-quote-id" },
      "quantity": 2,
      "promisedDate": "2026-10-01"
    }
  ],
  "expectedDeliveryDate": "2026-10-01",
  "paymentTermsSnapshot": "Net 30"
}
```

服务端从 `orderLineId`、供应商报价和当前数据库关系补全件号、RFQ 行、成本、行总额和供应商；不接受顶层 `partNumber`、顶层数量、客户端合计或伪造的供应商 ID 作为事实。`MANUAL` 来源必须另带正数 `unitCost`、原因和可审计证据，并只允许有采购/财务成本能力的主体使用。

`submit` 冻结创建输入并生成审批快照；`approve` 的请求只含 `version`、意见，服务端按 Decimal 合计选取 MANAGER/FINANCE/GM 并执行禁自批；`reject` 必须有原因；`confirm` 追加供应商确认记录和独立 `supplierReferenceNo`，不能覆盖已审批价格。`receipts` 只接收明确承诺行、数量、实物身份、证书和证据，随后调用库存服务；`direct-ship-evidence` 只能在 D05 直发适配器已开放时接受，当前应阻断。

### 5.2 结算摘要

```text
GET  /api/settlements?referenceType=ORDER|PURCHASE_COMMITMENT&referenceId=&direction=
GET  /api/settlements/:id
POST /api/settlements
POST /api/settlements/:id/entries
POST /api/settlements/:id/reconcile
```

`POST /settlements` 要求 `direction`、真实引用、USD 金额快照、明确到期日、外部系统和外部凭证号；服务端以订单行或采购承诺行重新计算金额并拒绝不一致。`entries` 只接受带外部付款/冲销凭证的追加分录；`reconcile` 更新外部核对状态和时间，不向总账写入。销售安全响应可只返回 `amount/outstanding/dueDate/status`，应付单位成本和供应商凭证需要财务能力。

## 6. OWN、背靠背和直发的连接方式

```text
RFQ/RfqLine
   ├─ SupplierQuote ──> PurchaseCommitmentLine ──> receipt/direct-ship evidence
   └─ QuotationLine ──> OrderLine ──> AR summary

OWN receipt/stock ──> InventoryAllocation ──> AllocationAssignment
                   ──> FulfillmentReview ──> OUTBOUND ──> Shipment/receipt
```

- **OWN 销售**：报价接受后直接走现有 D12 分配和 D05/D13 质量、出库、发运链路，不创建采购承诺或 AP 摘要。订单可以有应收摘要；库存成本仍按 D03 响应政策脱敏。
- **背靠背采购转售**：客户 `OrderLine` 成交后为每个需求行创建采购承诺行，逐行跟踪供应商确认、收货和缺口。采购承诺不是销售成交的替代品，也不能让供应商 `isWinner` 直接变成订单。采购收货变成公司 OWN 库存后，仍必须通过 D12 分配和 D05 质量审核履约。
- **部分采购/部分成交**：订单行 10 件可以由两个承诺按 6+4 覆盖；每个承诺只绑定实际 `OrderLine`，活动总量不超过 10。客户报价部分成交、商业修订或供应商报价变更都不能用旧头部数量重置已绑定行。
- **供应商直发**：承诺行仍绑定订单行和供应商，但没有本地库存数量可供伪造 OUTBOUND。直发证据必须含供应商发运/签收、实物身份、适用证书和 D05 质量复核；质量复核与接收人分离，附件版本变化使旧结论失效。未开放前所有直发完成/结算动作返回明确阻断。

## 7. 验收清单

### 7.1 来源、金额和编号

1. 用两条 RFQ 行、两条报价行和一张两行现代订单创建承诺；每行能从 `orderLineId -> quotationLineId -> rfqLineId -> supplierQuoteId` 追溯，跨 RFQ 行、跨供应商、件号不匹配、来源过期、历史币种待核均返回 4xx，数据库不留半条承诺。
2. 复用一个供应商报价创建两条承诺时，累计承诺量不能超过订单行成交量；同一行 6+4 合法，第三次超过余量回滚。承诺头总额严格等于 Decimal 行总和，`10000.3706` 等四位金额不被 Float 舍入。
3. 订单客户 PO、AeroLink 销售订单号、内部采购承诺号和供应商 PO/确认号在 API、CSV、合同和审计中各自有字段。写入客户 PO 不会自动生成或覆盖供应商 PO。
4. 非 USD 采购承诺、结算摘要、供应商来源全部拒绝；历史 `currency = NULL` 不静默当作 USD。

### 7.2 审批、范围和并发

5. 使用 `4,999.99`、`5,000`、`50,000`、`50,000.01` 四个金额边界核对 MANAGER/FINANCE/GM；创建人审批返回 `SELF_APPROVAL_FORBIDDEN`，销售、质量、无授权财务均拒绝。两个审批请求争用同一 `version` 只有一个成功。
6. 销售只能读取自己/部门关联订单的供应商状态、交期和缺口，不能看到 unit cost、AP 摘要或供应商付款条款；质量经理能读取当前订单所需质量上下文而不需要 `quotation.read`；跨 owner/department 的订单读取和写入均拒绝。
7. 同一 `Idempotency-Key` 重试只返回同一承诺/结算分录；同键不同请求、过期缓存后的重复命令、两个并发收货或两个并发付款都不能重复占量或重复入账。所有失败事务包括幂等记录和 outbox 一起回滚。
8. APPROVED 后修改价格、供应商、RFQ 行或承诺量被拒绝；修订必须创建新承诺并保留原审批和确认记录。取消只释放未收货余量，不删除已收货、质量或付款证据。

### 7.3 收货、质量和交付

9. 背靠背手工收货经 D14 adapter 调用库存服务，只产生一条有 `INBOUND` 前后数量的库存流水，并带承诺行来源；不能直接 PATCH 数量、allocatedQuantity 或绕过 D12 创建发运。
10. 收货数量、件号、批次/序号、证书状态、货架期或寿命不符时拒绝；质量人员需独立创建审核并绑定当前证据哈希，审核附件撤销/变更后旧结论失效。采购经办人不能审批自己的质量事实。
11. 直发在当前阶段明确返回未开放；启用后用独立合成交易验证：无本地 OUTBOUND 也不能假造库存扣减，但供应商运单、签收、实物证据和 D05 质量审核齐全前不能 SHIPPED/DELIVERED/COMPLETED。
12. 采购承诺已确认但未收货/未完成质量时，客户订单保持实际可交付余额；供应商确认不能单独增加 `OrderLine.outboundQuantity` 或客户签收量。D13 的多运单、签收和退货分别核对，不把商业冲销当作库存退货。

### 7.4 应收应付对账

13. 一张订单生成应收摘要，一张采购承诺生成应付摘要；金额、币种、到期日和外部凭证可追溯。没有外部凭证时不能标记已收/已付或已结清。
14. 添加客户回款、供应商付款、部分冲销和冲销撤回后，摘要的已收/已付、冲销和欠款由分录重算；负数、超额、重复外部凭证、跨方向引用和同键重复均拒绝，原付款记录不被删除。
15. 结算接口、导出和事件不写总账、不触发真实付款；与外部财务系统仅保存凭证号、金额、日期、状态和最后核对时间。财务能看到 AP 成本，销售只看到授权的 AR 状态。

## 8. 实施顺序和退出门槛

1. 先在能力策略中加入 `purchase_commitment.*`、`settlement.*`，冻结上述状态、金额级别、供应商 PO/客户 PO 命名和 `SUPPLIER_DIRECT` 开关；为每种拒绝建立错误码。
2. 增加采购承诺头、行、确认/事件和结算摘要/分录的迁移。历史 SupplierQuote、Order、OrderLine 不自动生成承诺或付款记录；迁移后做 Decimal/关系只读对账。
3. 实现服务层的 DB 关系重查、范围判断、来源快照、CAS、幂等、Serializable 和 outbox，再接 HTTP/OpenAPI。所有响应先做安全投影，不能等前端隐藏成本。
4. 实现背靠背收货 adapter，复用库存服务和 D12/D05/D13；直发只在适用质量服务完成并有独立真实证据后打开。之后再接结算摘要和外部分录。
5. 用独立 PostgreSQL 库执行本清单的两行、部分采购、四档审批、并发、质量阻断、直发阻断、AR/AP 分录和权限反例；最后再做真实浏览器的采购待办和财务对账页面。完成前不能宣称背靠背主营业务闭环或 M3 已达标。
