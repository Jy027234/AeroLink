# D14 采购承诺与销售结算实施设计

日期：2026-09-09。本文描述当前模型和下一阶段实施边界。数据库基础、采购命令、采购 HTTP 契约、安全投影及后台收货/独立验收路径已实现；直发、结算持久化和岗位页面仍未完成。采购阶段证据见 [采购承诺命令与接口阶段记录](D14_采购承诺命令与接口验收.md)，收货阶段验收另行记录。

## 1. 范围和固定口径

D14 面向两种销售来源：公司自有库存销售，以及成交后向供应商采购再转为公司库存的背靠背销售。客户订单/客户 PO 与供应商采购承诺/供应商参考号是两条独立事实，不能共用字段或互相推导。首期只使用 USD；金额使用 `Decimal(18,4)`，审批沿用总额 `<= 5,000` 为 MANAGER、`> 5,000 && <= 50,000` 为 FINANCE、`> 50,000` 为 GM 的规则，创建人和提交人不能审批自己的承诺，AOG 不绕过金额级别。

当前采购承诺状态只有：

`DRAFT`、`PENDING_APPROVAL`、`APPROVED`、`CONFIRMED`、`CLOSED`、`REJECTED`、`CANCELLED`。

`SUPPLIER_DIRECT` 的数据库列已存在，但本批 `directShippedQuantity` 固定为 0。供应商直发必须等后续真实运单、签收、质量审核和证据链完成后再开放。

`receivedQuantity` 只表示已经验收且可进入库存分配的数量。仅到货、待检和拒收不计入该列，由 `StockReceipt/StockReceiptLine` 保存独立到货和质量事实。

## 2. 当前可复用的模型和代码入口

| 事实 | 当前模型或代码 | 可复用内容 | 当前限制 |
| --- | --- | --- | --- |
| 需求与报价 | `RFQ`、`RfqLine`、`Inquiry`、`InquiryItem`、`SupplierQuote` | 精确 RFQ 行、供应商、件号、报价数量、USD 核实、有效期 | 供应商报价不是采购承诺；当前报价价格/数量变化不能改写已保存采购快照 |
| 销售成交 | `Quotation`、`QuotationLine`、`Order`、`OrderLine` | 成交客户、现代订单行、销售行与 RFQ 行关系 | `Order.poNumber`/`poNumberCustomer` 是客户 PO 语义，不能写供应商 PO |
| 自有库存履约 | `InventoryAllocation`、`AllocationAssignment`、`InventoryTransaction` | 来源明确、数量守恒、CAS、幂等和 D12 分配链 | 不能用采购承诺替代库存分配，也不能伪造 OWN 出库 |
| 质量与交付 | `FulfillmentReview`、`Shipment`、`ShipmentLine`、`ReturnHold` | 身份、证书、寿命、附件版本/哈希、质量审批、签收和退货事实 | 供应商确认不等于收货或交付完成 |
| 采购命令、策略与投影 | `server/src/modules/procurementSettlement/` | 审批快照、覆盖量、永久命令事件、采购 HTTP 及成本投影 | 结算仍为金额纯函数，没有结算 HTTP 路由 |
| 到货与验收 | `StockReceipt`、`StockReceiptLine`、`StockReceiptEvent` | 独立送货编号、整行待检/验收/拒收、证据指纹、唯一入库流水 | 尚无岗位收货页面；拒收不是供应商退货或财务冲销 |

`purchaseAccess.ts` 以当前 `Order -> Quotation.createdBy/creator.department` 计算 owner/部门范围，并要求订单为现代行模式，同时要求 `order.read` 和 `purchase_commitment` 对应能力。成本字段只有 `purchase_commitment.view_cost` 通过时才投影。该文件是服务层读辅助，不是已完成的 API 入口。

## 3. 已落地的数据库基础

迁移文件：`server/prisma/migrations/20260909000300_purchase_commitments/migration.sql`。

### 3.1 `PurchaseCommitment`

当前 schema 字段为：

- `id`、唯一 `commitmentNumber`、`orderId`、`supplierId`、`currency`（默认 `USD`）、`totalCost Decimal(18,4)`；
- `status`、`version`、`createdById`；
- `submittedById/submittedAt`、`approvedById/approvedAt`、`approvalLevel`、`approvalPolicyVersion`、`approvalSnapshot`；
- `confirmedById/confirmedAt`、`supplierReferenceNo`、`confirmationEvidence`、`paymentTerms`、`createdAt`、`updatedAt`。

头只关联一张销售订单和一个供应商。没有独立的头级履约模式字段，履约模式在每个采购承诺行上表达。所有历史关系外键使用 `RESTRICT`。

### 3.2 `PurchaseCommitmentLine`

当前 schema 字段为：

- `purchaseCommitmentId`、`lineNo`、`orderLineId`、可空 `sourceSupplierQuoteId`；
- `partNumber`、`uom`、`quantity`、`cancelledQuantity`、`receivedQuantity`、`directShippedQuantity`；
- `unitCost Decimal(18,4)`、`lineTotal Decimal(18,4)`、`currency`、`promisedDate`；
- `fulfillmentMode`（`STOCK_RECEIPT` 或 `SUPPLIER_DIRECT`）、`sourceSnapshot`、`identitySnapshot`、`version`、`createdAt`。

`(purchaseCommitmentId,lineNo)` 和 `(purchaseCommitmentId,orderLineId)` 唯一。行必须属于头的 `Order`，对应 `OrderLine -> QuotationLine -> RfqLine`，且订单保持 `lineItemsMode=true`；`partNumber/uom` 与订单行一致。非空来源报价必须匹配头供应商、对应 RFQ 行和件号。来源报价的价格、数量和有效期不会在后续计数更新时重新读取，历史事实保存在 `sourceSnapshot`；被引用报价的供应商、RFQ 行和件号身份不能修改，删除受外键阻止。

数据库检查包括 USD、非负金额、正整数数量、三类计数总和不超过 `quantity`、`lineTotal = unitCost * quantity`、`directShippedQuantity = 0`，以及头 `totalCost` 等于全部行 `lineTotal` 的延迟事务校验。草稿外商业字段不能原地改写；确认后行只能单调增加合法计数；非草稿头不能新增行；事件和创建身份只能保留，不能更新或删除。

### 3.3 `PurchaseCommitmentEvent`

事件字段为 `purchaseCommitmentId`、`kind`、`actorId`、`commandId`、`eventNo`、`requestHash`、`data`、`createdAt`。唯一键是 `(commandId,eventNo)`，事件只追加。该表记录状态、来源和数量变化的审计边，不能替代后续收货、质量或付款事实。

## 4. 当前纯函数和策略口径

### 4.1 审批快照

`purchasePolicy.ts` 要求头、行和来源快照均为 USD，金额为有限且不超过 `Decimal(18,4)` 的非负值；每行 `unitCost * quantity` 必须等于 `lineTotal`，头金额必须等于行合计。行 ID、行号和销售来源行不能重复。

`identitySnapshot` 当前需要 schema 版本、订单行/报价行/RFQ 行、件号、UOM、条件、序号/批号（可为空）、证书要求和证书类型。`sourceSnapshot` 保存 schema 版本、供应商、RFQ 行、件号、USD、单位成本，并且：

- `SUPPLIER_QUOTE` 必须带来源报价 ID、足够的报价数量和有效日期；
- `MANUAL` 必须没有供应商报价 ID，并带原因及可校验的附件 ID、版本、状态和 SHA-256。

服务端仍需在创建、提交或审批时重新读取订单、供应商和报价关系；快照校验不能替代事务内的当前对象权限和关系检查。

### 4.2 采购覆盖量

`procurementQuantities.ts` 接收销售行数量、采购事实和库存分配事实。它校验正整数/安全整数、分配释放与出库不超过原始分配、未知来源和重复 ID、未收货不能分配。采购有效覆盖量由 `quantity - cancelledQuantity` 推导；采购来源的库存分配和出库不应再次把同一销售需求计算一遍。函数同时返回未覆盖量、未收货余量、已收货未分配量和实际履约量。直发数量在纯函数中保留未来推导位置，但数据库本批固定为零。

### 4.3 应收应付金额推导

`settlementAmounts.ts` 目前是无持久化纯函数。输入是 USD 初始应收、初始应付和外部凭证事件，事件类型只有 `PAYMENT`、`CREDIT`、`REFUND`、`REVERSAL`，每个事件带 `RECEIVABLE` 或 `PAYABLE` 方向。

`PAYMENT` 增加该方向的付款，`REFUND` 减少有效付款，`CREDIT` 减少应付金额。`REVERSAL` 必须引用一个非 reversal 原事件，金额、方向和币种必须完全一致，原事件只能被反向一次，不能反向另一个 reversal。函数返回初始金额、有效付款、退款、信用冲减、调整后应付、未付、超付和待退款金额；它不写总账、不发起支付、不推导汇率，也不代表外部凭证已入账。

### 4.4 只读范围和成本投影

`purchaseAccess.ts` 返回采购状态、时间、行数量和履约模式等安全字段。没有成本能力时，不返回 `totalCost`、`unitCost`、`lineTotal`、`sourceSnapshot`、审批快照、确认凭证、付款条款或供应商参考号；财务/采购的成本读取仍必须经过当前 scope 和能力判断。

## 5. 采购接口与后续收货、结算接口

当前已实现的采购接口：

```text
POST /api/purchase-commitments
GET  /api/purchase-commitments?orderId=...
GET  /api/purchase-commitments/:id
POST /api/purchase-commitments/:id/submit
POST /api/purchase-commitments/:id/approve
POST /api/purchase-commitments/:id/reject
POST /api/purchase-commitments/:id/confirm
POST /api/purchase-commitments/:id/cancel
```

采购创建请求只提交订单行、来源类型/ID、数量、交期和必要的人工成本证据；件号、UOM、来源成本、行总额和两个快照由服务端从当前关系生成并在事务中重查。所有写操作需要幂等键、Serializable 事务、事件和安全 outbox 投影；现有承诺的状态操作另要求当前 `version`。库存与活动采购的共同覆盖量已有数据库约束。

已实现后台收货接口：

```text
POST /api/stock-receipts
GET  /api/stock-receipts?orderId=...
GET  /api/stock-receipts/:id
GET  /api/stock-receipts/lines/:id/review-context
POST /api/stock-receipts/lines/:id/review
```

只有 `CONFIRMED` 采购可以新增到货和质量决定。每个实际批次/序号记录一行；部分质量结果在到货时拆行，审核整行通过或拒收。到货、待检、拒收不创建可用库存或入库流水。独立质量人员不得是到货人或采购经办人；验收时重验当前需求链、证书、寿命和附件指纹，在同一个 Serializable 事务内创建 OWN 库存、唯一收货 INBOUND、验收状态和采购已收货量。拒收保留不可变历史，释放补送容量。

每条验收行拥有独立库存 `stockLotKey=receiptLine.id`，允许同批次、同仓库分次验收且不混合成本或证据。现有普通库存使用结构默认值 `LEGACY`，不推断历史采购来源。原采购分配必须显式引用该收货行并履约原销售行，消耗量持续占用其原始来源额度；真实已放行退货可以通过 `sourceReturnHoldId` 进入独立复售池，不补回已经消耗的采购额度。采购分配不重复计入销售需求覆盖量，退货复售按 OWN 覆盖新需求。

收货证据使用独立 `stock_receipt` 域，不允许把采购成本域文件重新归类；下载重验当前库存管理/质量能力、订单范围和精确附件指纹。质量 DTO 和刷新事件不包含采购成本。已有供应商证书按验收快照中的精确 ID/文件哈希进入后续 D12 出库复核，当前未签发、撤销、过期或哈希改变均阻断使用。收货阶段不修改证书归属来推断来源。

供应商直发不得伪造本地库存或 OUTBOUND；未完成适用质量审核、签收和证据校验时，不能推进交付完成。

结算接口仍需后续建模和迁移：应收引用 `Order`，应付引用 `PurchaseCommitment`，两者保留 USD 金额、到期日、外部凭证摘要和追加事件。持久化分录必须复用当前纯函数口径，不能把派生余额作为可任意修改字段，也不能扩大为总账、付款网关、税务或多币种系统。

## 6. OWN、背靠背与直发边界

```text
RFQ/RfqLine
   ├─ SupplierQuote ──> PurchaseCommitmentLine ──> StockReceiptLine/独立验收
   └─ QuotationLine ──> OrderLine ──> 后续应收摘要

OWN 库存 ──> InventoryAllocation ──> AllocationAssignment
          ──> FulfillmentReview ──> OUTBOUND ──> Shipment/签收
```

- OWN 销售直接使用现有 D12/D13 履约链，不创建采购承诺。
- 背靠背采购逐个绑定现代 `OrderLine`，采购收货进入 OWN 库存后仍需要 D12 分配和质量审核。
- 同一销售行可以由多个承诺拆分覆盖，但活动承诺总量、取消、验收和履约量必须分别守恒，不能用订单头部数量猜测。
- 直发仅是行级履约模式的后续扩展，当前数据库和服务不得把它当作已完成交付。

## 7. 完整 D14 的退出条件

1. 采购创建、提交、审批、驳回、确认和范围读取具备真实 HTTP/OpenAPI 契约，所有写入具备幂等、CAS、Serializable 和事件审计。
2. 采购收货持久化复用库存服务，能记录待检/验收/拒收，验收可用量与 D12 分配严格衔接，并有权限和证据反例。
3. 直发拥有真实供应商运单、签收、身份、质量审核和附件版本链，不能绕过本地库存规则或错误推进订单完成。
4. 应收/应付摘要和外部凭证分录具备持久化、幂等、范围投影和反向事件验证，不写总账、不触发真实付款。
5. API、数据库并发、权限、成本脱敏和浏览器 UI 均完成独立验收。完成前只能称为 D14 基础阶段，不能宣称采购结算闭环或生产放行。
