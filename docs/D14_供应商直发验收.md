# D14 供应商直发：实现与验收记录

本记录属于完整 D14 的增量开发，不改变受控试用候选 `4ab3b1c61c9dd3d6997abd249884953acc15932f`。该候选保留在独立 worktree，本轮直发代码及迁移未进入该候选。直发尚未完成全部验收，不代表背靠背结算闭环或用户试用放行。

## 已实现范围

- 已确认采购行使用 `SUPPLIER_DIRECT` 履约模式，建立供应商运单、实际批次/序号和附件指纹。
- 创建计划、逐行独立质量决定、发运、取消和分次客户签收分别为受控命令；写接口使用当前权限、版本、幂等键、Serializable 事务及延迟约束验收。
- 审核人不得是直发创建人或采购创建/提交/确认人；实际发运人不得同时是该批质量审核人。批准需要四项检查通过并重验当前质量事实。
- 发运前再次校验审核快照和附件版本。质量身份、证书、寿命或证据变化阻断发运。
- 直发单独累计采购和销售行的直发数量。客户签收不增加采购本地收货量，也不创建本地库存或 OUTBOUND；混合交付按本地与直发实际数量计算发运和签收完成。
- 待检计划占用采购额度；拒收或取消释放相应计划额度。取消采购前必须处理尚未结束的直发计划。
- 签收记录保留操作者、签收人文本、签收时间和附件。签收人文本是员工录入的凭证信息，不代表系统认证了客户身份。

## 已发现并修复的问题

1. 初版数据库约束要求头部证据为 JSON object，服务使用指纹数组。013 前向迁移改为非空数组，保留其他约束；未修改已应用的 011/012。
2. 事件约束只允许 RECEIPT 携带增量签收数量。CREATE、APPROVE、REJECT、DISPATCH 的 `quantity` 统一为 0，业务数量保留在相应事件 data 中，避免被当作签收增量。
3. 序号占用释放受即时触发器保护。取消命令先把头部改为 CANCELLED，再释放序号占用，最终在同一事务中验证事件和数量约束。
4. 审核请求字段统一为 `snapshotHash`，64 位 hex 规范为小写；路由通过采购结算模块公共入口导入。
5. 已拒收计划可以被新计划替代。即使新计划已经完成订单交付，旧的未发运计划仍可取消；取消不会撤回实际交付。

真实数据库首次命令试跑暴露了额外触发器问题：订单头触发器解析不存在的 `NEW.orderId`，使采购创建在延迟约束阶段回滚。014 修复跨表字段解析后，代码审查又发现订单行 ID 比对与延迟事件旧计数的误判风险。015 已修复并部署：区分订单行 ID 与订单头 ID，在延迟约束实际执行时读取最终数据库计数。不得把空表语法检查当作真实有量场景的通过证据。

重新生成 OpenAPI 时，还发现生成器会覆盖候选中的证书禁用续期和撤销理由约束。已修复生成源并在 `check-generated.mjs` 添加回归断言。后续页面集成另外补齐采购来源 SUPPLIER_QUOTE/MANUAL discriminator 映射、订单及分配 DTO 的直发计数；这些变更均已回写生成源。
