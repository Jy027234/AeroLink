# D12 数量分配实施设计

> 状态：设计稿，供下一阶段迁移和真实 PostgreSQL 验收使用。本文只描述方案，不代表当前代码已经支持多批次分配。

## D10/D11 完成后的实施校正（2026-09-08）

以下决策优先于本文早期的单表分配草案；后续迁移和 API 必须以此为准。

- D10 已允许现代报价部分成交、多次生成订单；只对旧单行保留报价到订单的部分唯一索引。`Quotation.orderId/orderNumber` 是最新订单兼容投影，不能用来推断分配归属。
- 采用库存来源 `InventoryAllocation` 与订单分配 `AllocationAssignment` 两层。一条来源预留可明确分配给多个 `OrderLine`；不反复改写单个 `orderLineId`，也不把转移伪装成释放后重新预留。
- 父记录保留 `allocatedQuantity/releasedQuantity/consumedQuantity`，子记录保留 `assignedQuantity/releasedQuantity/consumedQuantity`。父消费必须等于子消费总和；父释放包括未分配部分释放及子分配释放。活动物理占用等于未分配数量加各订单活动分配总和。
- `QuotationLine.reservedQuantity` 投影为尚未分给订单的报价预留；订单占用由 assignment 汇总。部分成交必须按明确来源和数量分配，不能通过第一批库存或报价头的最新订单推断。没有库存分配的订单不能出库。
- D11 修订和报价到期只释放未绑定订单的报价预留。既有订单即使尚未出库，也必须保留其活动分配；新修订不继承旧版分配。失败时释放与修订一起回滚。
- 首个代码增量 `allocationQuantities.ts` 只实现计数守恒校验，8 项测试通过；尚无数据库表、写 API、库存分配或出库功能。后续仍须实现全部写入口的并发保护、权限、事件、质量审核关联和真实 PostgreSQL 验收。

## 1. 范围和边界

D12 解决“一个报价/订单行可以由多个库存批次或序号件组成”的数量分配问题。当前库存服务仍是应用内部的预留、出库和审计边界；用户 ERP 主账问题尚未确定，因此本文不把 `InventoryDetail` 或拟议的 Allocation 声明为 ERP 唯一主账，也不设计向 ERP 写回。后续如接 ERP，应通过带外部幂等键的适配器和对账流程接入。

本设计与 D10 的 `RfqLine`、`QuotationLine`、`OrderLine` 一起实施。旧报价/订单头上的数量字段在兼容期保留为聚合投影，新的分配命令以行 ID 和库存明细 ID 为准。成本字段、客户价格、毛利和任何成本快照都不进入分配响应、事件或质量证据。

## 2. 当前数据模型和所有写入口

### 2.1 当前字段语义

- `InventoryDetail.quantity` 是当前在手数量。预留不会减少它，出库才会减少它。
- `InventoryDetail.status` 目前把整条明细标成 `AVAILABLE` 或 `RESERVED`，不能表达一个批次部分预留、另一部分可用。
- `Quotation.reservedQuantity` 和 `Order.outboundQuantity` 是单行头字段；D10 已有同名的 `QuotationLine.reservedQuantity`、`OrderLine.outboundQuantity`。
- `InventoryTransaction` 记录实物数量的 before/after，但当前预留事件的 `quantity` 为 0，没有 Allocation 外键或命令幂等键。
- `FulfillmentReview` 绑定 `orderId + inventoryDetailId`，快照中有计划数量、明细数量/状态、批次/序号和证据；它尚未绑定具体的分配行。

## 3. 建议的 Allocation 模型

### 3.1 一行多批次的基本单位

建议新增 `InventoryAllocation`，**一行 Allocation 表示一个目标交易行从一个 `InventoryDetail` 批次/序号明细得到的一段数量**。一个 `QuotationLine` 或 `OrderLine` 可以有多行 Allocation，因此同一行可拆到多个批次；同一批次也可以服务多个交易行，只要活动数量总和不超过在手量。

建议字段如下，具体命名可由迁移实现确定：

```text
InventoryAllocation
  id                    UUID PK
  quotationLineId       FK QuotationLine.id NOT NULL
  orderLineId           FK OrderLine.id NULL      -- 订单创建后绑定
  inventoryDetailId     FK InventoryDetail.id NOT NULL
  allocatedQuantity     positive Int NOT NULL
  releasedQuantity      Int NOT NULL DEFAULT 0
  consumedQuantity      Int NOT NULL DEFAULT 0
  status                ACTIVE/PARTIAL/RELEASED/CONSUMED/CANCELLED
  commandId             FK AllocationCommand.id NOT NULL
  commandLineNo         positive Int NOT NULL
  createdById            FK User.id NOT NULL
  releasedAt            DateTime NULL
  consumedAt            DateTime NULL
  releaseReason         String NULL
  createdAt/updatedAt   DateTime
```

不使用一个可变的 `remainingQuantity` 作为唯一事实。数据库约束和服务校验必须保持：

```text
0 < allocatedQuantity
0 <= releasedQuantity
0 <= consumedQuantity
releasedQuantity + consumedQuantity <= allocatedQuantity
activeQuantity = allocatedQuantity - releasedQuantity - consumedQuantity
```

`status` 可由计数派生并作为查询索引；计数是审计和并发更新的事实。幂等键保存在命令级记录 `AllocationCommand`，唯一约束为 `(actorId, operation, requestKey)`，并保存完整请求摘要和响应；已有通用幂等记录可以复用其职责。分配行用 `(commandId, commandLineNo)` 唯一约束。一条多批次命令可创建多行分配，同键异参拒绝，不在每条分配上重复设置 actor/requestKey 唯一约束。

### 3.2 Allocation 事件和实物流水

建议新增不可变的 `InventoryAllocationEvent`，或在现有 `InventoryTransaction` 上增加等价字段：

```text
allocationId, quotationLineId, orderLineId,
operationKey, operationType(RESERVE/RELEASE/CONSUME),
quantity, allocatedBefore/After, releasedBefore/After,
consumedBefore/After, actorId, createdAt
```

事件键 `(commandId, allocationId, operationType)` 必须唯一；`operationKey` 为命令内派生键，重放只返回已提交事件及原响应。实物 `InventoryTransaction` 继续记录 `INBOUND/ADJUSTMENT/OUTBOUND` 的库存 before/after，并带上 `allocationId` 和行 ID；预留/释放可以有数量为 0 的实物流，但 Allocation 事件不能省略。这样能区分“保留了多少”与“实际扣减了多少”，也能在当前旧的零数量 RESERVATION 流水不足时识别迁移不确定性。

不使用 `targetType + targetId` 的多态外键。报价行和订单行使用显式 FK，服务层保证一个 Allocation 先属于 `QuotationLine`，绑定订单后同时有 `OrderLine`；当历史数据无法确定对应行时阻断回填而不是按编号猜测。

### 3.3 数量和状态的来源

对某个 `InventoryDetail`：

```text
activeAllocated = Σ(allocation.allocatedQuantity
                     - allocation.releasedQuantity
                     - allocation.consumedQuantity)
availableQuantity = inventoryDetail.quantity - activeAllocated
```

预留和释放不改变 `InventoryDetail.quantity`；出库同时增加 `consumedQuantity`、减少 `InventoryDetail.quantity`，并写 OUTBOUND 实物流水。`availableQuantity` 不能为负。

`InventoryDetail.status` 保留为库存质量/可用状态。`QUARANTINED`、`SCRAPPED` 等状态直接禁止新的 Allocation；批次有部分活动 Allocation 但仍有余量时保持 `AVAILABLE`，不能把整批改成 `RESERVED` 后误阻断余量。兼容旧单行接口时，只有“整条明细被占满”或序号件被占用才可以投影成 `RESERVED`；旧接口遇到部分分配、多批次或多行应返回明确的兼容错误，不能静默选第一批。

## 4. 预留、释放和出库流程

### 4.1 预留

1. 命令输入改为 `quotationLineId`、`allocations: [{ inventoryDetailId, quantity }]` 和幂等键；旧的 quotation ID 入口只解析 D10 单行并限制单批次。
2. 根据当前数据库中的 quotation、RFQ、quotation line、供应商报价和部门重新检查所有权、能力、状态、part number、condition、需求剩余量以及批次/序号约束。不能信任旧缓存、请求中的 owner 或 JWT claim。
3. 在 PostgreSQL `SERIALIZABLE` 事务中按 `inventoryDetailId` 排序锁定明细，再锁定 quotation line（若已有订单则锁定 order line）。重新计算每个明细的 `availableQuantity`，总数不足时整批失败，不接受部分静默成功。
4. 为每个来源明细创建一行 Allocation，并创建 RESERVE Allocation 事件；同一事务更新 `QuotationLine.reservedQuantity` 投影及兼容头字段。新订单已存在时绑定对应 `OrderLine`，否则订单创建必须在同一事务把相关 Allocation 绑定到生成的行。
5. 对序号件要求 `quantity = 1` 且该 detail 没有其他活动 Allocation；对批次件允许多个交易行共享，但活动总数必须不超过 `InventoryDetail.quantity`。
6. 提交后发布只含实体 ID、行 ID、变化类型和刷新提示的 outbox 事件，不带 unitCost、价格或客户信息。相同 request key 的重试只返回第一次结果。

### 4.2 释放

释放命令以 `allocationId` 或 line 下的明确 Allocation 集合为目标，不能仅靠当前 `inventoryDetailId` 重新推断。事务中锁定 Allocation、来源明细和交易行，检查未消费部分，增加 `releasedQuantity`，写 RELEASE 事件并更新行级/头级投影。

整单撤回必须先在同一事务释放所有活动 Allocation，再改变 quotation 状态；一条 Allocation 已部分出库时只释放未消费部分，已消费数量不能回滚成可用量。仅当该明细没有其他活动 Allocation 且没有质量阻断时，才把兼容状态投影回 `AVAILABLE`。重复 release request 返回原事件，不得产生第二次释放。

### 4.3 出库

出库命令以 `orderLineId + allocationId + quantity` 为最小目标。事务顺序固定为：当前 owner/部门和 capability 复核 → 锁定 order line、Allocation、InventoryDetail（按 ID 排序）→ 校验订单/行剩余量、序号/批次和当前数量 → 校验并一次性消费质量审核 → 更新 Allocation consumed 计数和 CONSUME 事件 → 扣减 `InventoryDetail.quantity` 并写 OUTBOUND 流水 → 更新 `OrderLine.outboundQuantity`、报价行预留投影和订单头投影。

一个 order line 的多批次出库要逐 Allocation 处理，不能因为某一个批次完成就把整个订单标成 SHIPPED。只有所有 order line 的目标数量都由 Allocation 消费完成才允许完成订单。部分出库应保留剩余 Allocation；释放与出库并发时只能有一个事务先取得行锁，另一个按最新计数返回冲突或只消费剩余量，不能出现负数或双重扣减。

当前 `FulfillmentReview` 必须扩展 `allocationId`（并建议加 `orderLineId`）或增加等价的 Allocation 明细集合。审核快照需锁定具体 detail、Allocation、计划数量和当前版本；同一审核只能被一个相同数量的 consume 命令消费一次。旧的仅 `orderId + inventoryDetailId` 审核在多批次模式启用前必须完成回填，否则该范围保持阻断。审核快照和事件仍禁止成本字段。

## 5. 幂等、并发和直接写保护

- 预留、释放、出库、质量审核消费都必须经过现有 `runIdempotentOperation`，并把 request key、用户、目标行、请求摘要和最终响应绑定。建议 Allocation 事件再加数据库唯一键，避免缓存失效后重复执行。
- 所有来源明细按稳定 ID 排序后锁定；再锁定 quotation/order line 和目标 Allocation。使用 PostgreSQL `SERIALIZABLE`，对 serialization failure/deadlock 做有限次数重试（例如 3 次），仍失败返回可重试的 409/503，而不是继续盲写。
- Allocation、行计数和实物流水必须在同一事务提交；outbox 事件在同事务写入，提交后异步投递。不能先发“预留成功”再写库存。
- 现有 `PATCH /inventory/:id` 在存在活动 Allocation 时拒绝 quantity 直接修改；数量调整必须走受控调整命令，校验 `newQuantity >= activeAllocated`。状态调整不能绕过 QUARANTINED/质量审核规则。
- `Quotation.reservedQuantity`、`QuotationLine.reservedQuantity`、`Order.outboundQuantity`、`OrderLine.outboundQuantity` 只能由投影函数更新。状态转换接口拒绝调用方传入这些计数，避免 `transactionStateService` 的通用 data 合并覆盖新值。
- 每次读缓存、事件重放和下载相关响应都按当前对象 owner/department/capability 重验；撤销/禁用用户不能继续消费已建立连接或收到敏感事件。分配事件仅发送变化提示，客户端重新请求授权后的数量视图。

## 6. 序号件、批次数量与数据库约束

### 序号件

现有 `unique_serial_per_item` 继续保证同一库存主件的序号唯一。序号明细必须 `quantity = 1`；一个有效/活动 Allocation 只能占用它一次，第二个并发请求返回 409。建议增加活动 Allocation 的部分唯一索引，或在明细行锁保护下用服务约束实现，二者不能只靠前端检查。序号件出库后不得再次分配，即使物理数量已被错误回填也要有状态/流水阻断。

### 批次件

现有 `[inventoryItemId, batchNumber, conditionCode, warehouse]` 唯一键继续防止同库存位置重复批次。一个 detail 可对应多个 Allocation；所有活动 Allocation 的 `activeQuantity` 之和必须不超过 `quantity`。同一请求的多条来源明细必须属于同一有效交易行、part number 和允许的 condition，按业务规则明确是否允许跨仓；默认不允许隐式跨仓。

### 建议约束

- 所有 Allocation 计数 `CHECK` 如上，数量为正整数。
- `quotationLineId`、`inventoryDetailId` 非空；`orderLineId` 在订单创建后必须存在且属于同一 quotation/rfq 链。
- Allocation 的 `allocatedQuantity` 不得超过行需求/接受量；投影计数不得超过行数量。
- `InventoryTransaction` 的 before/after 保持连续；OUTBOUND 的物理数量只能下降，INBOUND/ADJUSTMENT 按受控命令处理。
- Allocation 事件 `operationKey` 唯一，且同一 Allocation 的 released/consumed 总量不得超出 allocated。
- 数据库约束只承担不变量，所有权、部门、能力、报价状态和质量审核仍必须在服务层按当前对象读取后检查。

## 7. 与 D10、质量审核、所有权和成本脱敏的兼容

1. D10 回填顺序必须是 `RfqLine -> InquiryItem.rfqLineId -> SupplierQuote -> QuotationLine -> OrderLine`，然后才生成 Allocation。Allocation 只能引用同一报价的 `QuotationLine`，订单绑定只能引用其对应的 `OrderLine`；不接受跨 RFQ 行的 ID。
2. 第一阶段保留一个 quotation 一个 order 的现有约束，但允许每个订单包含多个 `OrderLine` 和每行多个 Allocation。若以后允许一个 quotation 多个 order，应另做关系迁移、订单归属和幂等设计，不在 D12 隐式放开 `Order.quotationId @unique`。
3. `FulfillmentReview` 的 owner、部门、审核者能力和证据所有权继续按当前数据库对象检查。质量检查必须针对具体 Allocation 数量和当前 detail 版本；不能用创建审核时的旧 owner 或提交请求中的 owner。
4. Allocation API、outbox、InventoryTransaction 扩展字段、质量快照和错误响应全部经过现有成本策略。没有 `inventory.view_cost` 的角色仍可读数量/状态/批次所需的非成本字段，但不返回 unitCost、总值、毛利、客户价格或包含这些值的自定义快照。
5. 事件只包含 `allocationId`、quotationLineId/orderLineId、inventoryDetailId、变化类型和版本/刷新提示。前端通过 QueryClient 重新请求当前授权数据，重连也触发刷新；不会通过事件携带成本或客户内容。

## 8. 旧单行数据映射和迁移门槛

### 8.1 迁移前预检

迁移脚本必须先只读生成报告，至少检查：

- D10 行回填完整，所有报价/订单头能唯一映射到行；无孤儿 `rfqLineId`、`quotationLineId`、`orderLineId`。
- 每个 `InventoryDetail` 的 quantity/status、序号/批次唯一性和实物流水 before/after 连续。
- `Quotation.reservedQuantity`、`QuotationLine.reservedQuantity`、`Order.outboundQuantity`、`OrderLine.outboundQuantity` 均非负且不超过相应需求。
- 活动旧预留都有明确 quotation、detail、part number、序号/批次和当前行；`RESERVED` 明细没有匹配预留的记录必须人工处理。
- `FulfillmentReview` 能映射到具体 order line 和 Allocation；已消费/未消费审核数量没有重复或悬空。
- 所有权/部门字段和审计 actor 可读取，成本字段不被复制到 Allocation 或事件。

任一门槛不满足就停止该范围迁移并输出 ID 清单，不自动猜 owner、RFQ 行、批次或历史数量。

### 8.2 可证明的旧预留

对于 `reservedQuantity > 0` 且明确绑定 `inventoryDetailId` 的单行报价，先完成单行 D10 回填，再创建一条 baseline Allocation：`allocatedQuantity = reservedQuantity`、released/consumed 为 0，request key 使用迁移批次和原报价 ID，事件标记 `LEGACY_BASELINE`。校验 `partNumber`、serial/batch、detail 状态和数量后，才能把它纳入新计算。

旧的 `RESERVED` 批次若对应多个可能报价，或报价已删除/owner 不可确定，必须阻断。不能把 `createdById` 当成当前单据 owner，也不能用第一条行记录填补缺失关联。

### 8.3 已出库但缺少历史预留量

当前出库会把 quotation 的 `reservedQuantity` 减少，旧 `InventoryTransaction.RESERVATION` 的 quantity 又是 0；因此仅凭当前头字段不能证明历史分配量。对于 `outboundQuantity > 0` 的旧订单，只有在订单、detail、OUTBOUND 流水和数量连续且来源唯一时，才可建立标记为 `LEGACY_CONSUMED` 的 Allocation（至少 `allocatedQuantity = consumedQuantity = outboundQuantity`，不虚构未保存的预留历史）。如果无法证明来源或存在多批次歧义，保留旧读模型并阻断启用该单据，不为了迁移绿灯猜测。

### 8.4 兼容期和启用条件

- 先部署只读 Allocation 投影和预检，再部署 Allocation-first 写路径；新写入不再直接改变旧头字段。
- 旧单行接口在能安全映射到一个行、一个 detail 时继续工作，响应由 Allocation 投影；遇到多行/多批次明确返回兼容错误，引导新接口。
- 迁移完成后，旧字段只读并由对账任务持续核对。启用开关按已对账数据范围逐步打开；回滚点放在启用新写入之前，启用后用反向投影和审计修复，不直接删除 Allocation 记录。
- 启用门槛：预检未知项为 0、孤儿 FK 为 0、Allocation 活动和投影计数一致、序号件活动唯一、所有质量审核可绑定、真实 PG 并发验收通过、成本字段扫描无泄漏。

## 9. 真实 PostgreSQL 并发验收脚本计划

应新增一次性脚本（建议 `server/src/scripts/checkInventoryAllocationConcurrency.ts`）和独立测试数据库；不得使用共享 `aerolink_review` 或生产库。脚本通过真实 API/服务入口创建合成用户和数据，结束时删除数据库/容器，不发送真实邮件、不连接 ERP、不把 token/cookie 写入仓库。

### 基础数据

- 一个批次库存 detail，quantity=10；一个序号 detail，quantity=1；另准备可用、隔离和不同仓库样本。
- 同一 RFQ 下两个 quotation line、对应 supplier quote、quotation/order line；不同部门 owner、peer、inventory manager、quality reviewer、无成本能力用户。
- 每条命令使用不同、可记录但不含秘密的测试幂等键；响应只断言 ID、数量、状态和版本。

### 必须通过的并发场景

1. 两个事务同时预留同一批次 6+6：一个成功、一个 409/可重试失败，活动总数 6，detail.quantity 仍为 10，可用量为 4。
2. 两个不同交易行同时预留 4+4：都成功，活动总数 8；第三个预留 3 被拒绝；释放其中 4 后可用量恢复 6。
3. 两个请求同时预留同一序号件：仅一个成功，另一个 409；任何重试不产生第二 Allocation。
4. 相同 request key 并发提交多批次请求：只有一组 Allocation、Allocation 事件和投影，两个调用得到同一幂等响应。
5. 注入 serialization failure/deadlock 后重试：最终只保留一次业务结果，不能重复写实物流水或 outbox。
6. 一个 Allocation 先部分出库 3，再并发出库 3/释放剩余：锁竞争后只能消费或释放合法剩余，detail 数量、Allocation 计数、订单行 outbound 和报价行 reserved 全部不为负且可对账。
7. 质量审核快照过期、数量不一致、证据被撤销、错误 order line 时全部拒绝；同一有效审核只能消费一次，重放只返回幂等结果。
8. 当前 owner/部门失效或能力撤销后，新的 reserve/release/outbound 和缓存响应均被拒绝；无成本能力用户仍可读数量视图但看不到成本字段。
9. outbox、Allocation 事件和 `InventoryTransaction` 在事务提交后各只有一条，before/after 连续；事务回滚时三者都不存在。
10. 运行 D10/legacy preflight：可证明的单行预留成功回填，歧义 RESERVED、旧多批次、无法恢复的历史 outbound 被列为阻断项，脚本不得自动猜测。

验收输出需记录数据库版本、迁移版本、并发参数、每个场景的成功/冲突计数和最终汇总查询；报告不得包含真实 JWT secret、token、cookie、成本或客户价。

## 10. 实施顺序

1. 先完成 D10 行回填和只读预检，冻结直接写旧计数的入口。
2. 增加 Allocation、Allocation event、InventoryTransaction/质量审核关联字段及约束，执行 shadow projection，对账不通过不开放写入。
3. 以事务服务实现 reserve/release/consume，保留单行兼容适配器；跑真实 PostgreSQL 并发脚本和质量/权限/成本反例。
4. 分阶段启用新写入，持续核对头字段与行/Allocation 汇总；处理所有旧数据阻断后再收紧旧接口。
5. ERP 边界、外部 reference 和回写策略另立决策；在决策前只输出内部 Allocation 状态和可审计对账结果。
