## 实际数据库结果

合成数据执行了以下正向流程：

1. 创建现代订单、订单行、RFQ 行和同供应商报价。
2. 创建采购承诺和一条 `STOCK_RECEIPT` 行，头金额等于行金额。
3. 依次推进 `DRAFT -> PENDING_APPROVAL -> APPROVED -> CONFIRMED`，保留审批快照和确认信息。
4. 将验收可用量增加 4；更新供应商报价价格/数量后，采购行的来源快照仍保持原值。

反例均按预期失败并回滚：

- 头商业字段、头身份/创建事实或确认后行身份被修改；
- 已确认行的验收计数回退；非草稿头新增零成本行；
- 供应商报价供应商、RFQ 行或件号身份被修改，或被引用报价被删除；
- 现代订单降级为旧行模式；
- 事件更新；
- `directShippedQuantity > 0`；
- 草稿行数量/行金额变化而头 `totalCost` 不变，延迟总额约束拒绝提交；
- 采购行与订单行、供应商、RFQ 行或件号关系不一致（见 `relation.sql`）。

这些是数据库和纯函数反例，不是 HTTP/API 验收；不能据此推断完整采购流程已经可用。

## 尚未实现或尚未验收

- 没有实际 `/api/purchase-commitments` 或 `/api/settlements` HTTP/OpenAPI 写入口，也没有真实 API 端到端验证。
- 没有 StockReceipt/待检/验收/拒收的持久化事实和库存适配器；数据库计数更新不是收货 API。
- 没有可用的供应商直发链、运单/签收/质量审核持久化；本批直发数量固定为零。
- 没有 SettlementSummary/SettlementEntry 持久化、外部应收应付凭证、对账入口或总账连接。结算验证只覆盖 `PAYMENT`、`CREDIT`、`REFUND`、`REVERSAL` 的金额推导纯函数。
- 没有采购待办、财务对账或成本权限的浏览器 UI 验收。
- 没有对生产数据库执行迁移、部署、真实邮件/付款或供应商直发。

完整 D14 还需要真实 API、收货与质量链、直发证据链、应收应付持久化、并发/权限/成本脱敏和浏览器验收全部通过后，才能另行出具业务放行结论。
