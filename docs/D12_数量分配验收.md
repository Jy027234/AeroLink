# D12 数量分配验收

日期：2026-09-09。状态：实现、真实数据库与浏览器联合验收已通过；D13 多批发运单、退货以及 D14 采购结算仍未完成。全部改动仅在本地分支 `codex/internal-safety-20260908`。

## 实现范围

- 库存父分配 `InventoryAllocation` 保存固定预留量；订单子分配 `AllocationAssignment` 保存显式分配给某订单行的数量。历史来源、初始数量、事件不可更新或删除，释放与消费计数只能递增。
- `InventoryDetail.allocatedQuantity` 等于全部父分配活动量；在手量只在实际出库时减少。报价行 `reservedQuantity` 只表示尚未分给订单的预留；订单行和订单头出库量由子分配消费汇总。
- 新增预留、分配、释放、出库和数量视图接口，强制幂等键；使用 Serializable 事务，P2034 最多重试三次。同一来源记录可分给多个订单行，禁止推断第一批库存或最新订单。
- 成交接受可逐行提交明确父分配切片。转入量不能超过本次成交量；成交后未分配预留不能超出剩余报价量。成交并分配需要库存管理权限；销售可普通成交，库存人员可在订单创建后补库。
- 修订和撤回只释放未分配部分，已绑定订单的活动分配保留。既有订单在原报价过期、撤回或被修订后仍可按当前库存与质量证据补库和履约。
- 质量审核绑定具体 assignment、计划数量、真实订单/RFQ 行、实物与证书指纹；经办人不能自审。证书件号、序号/批次、类型和有效状态必须匹配该实物；未指定批次的订单允许显式选择多批次来源。附件变化使旧审核失效，一条审核只消费一次。
- 自动到期释放由独立 Worker 每分钟执行；只释放到期父分配的未分配量，保留订单数量与未来到期预留。使用游标分页避免已耗尽历史记录阻塞后续处理；重复执行无第二个释放事件。
- 旧整单预留/释放/出库与库存直接数量修改拒绝活动现代分配；质量隔离和证据更新仍可进行，随后须重新复核。历史 Allocation 不自动回填，旧 RESERVED 和无法证明的历史 OUTBOUND 由只读对账列为人工阻断。
- 已有分配或出库历史的明细，禁止实际改写序号、批次或条件状态；共享主件存在分配或库存流水后，禁止实际改写件号及追踪类型。同值提交和说明、质量证据维护仍可进行。主件 PATCH 使用严格标量白名单，拒绝嵌套关系写入。
- 已出库序号不能通过手工补回在手量再次分配；D13 将增加关联原发运的受控退货及独立质量放行。释放命令在响应缓存被清理后仍校验历史事件中的规范化原因，同键异因或历史缺原因均明确冲突。
- 分配与库存刷新事件在同一事务持久化；接口只返回数量、身份和状态，不返回成本。订单交付只读页面按当前订单权限开放给质量人员，不要求其具备商业报价读取权限。

## 数据库与事务验证

独立 PostgreSQL 16 容器 `aerolink-review-test-20260908`，使用本机专用测试库；原 `aerolink_review` 未修改。Node `22.23.2`、npm `10.9.8`，新增迁移 `20260908000800_inventory_allocations` 后总计 25 条迁移。

`checkAllocationDatabaseInvariants.ts` 验证计数篡改、超分配、不平衡消费、消费倒退、低于已占用量的在手量、历史来源和事件更新/删除均被拒绝。其专用 schema 测试库包含故意不维护应用投影的原始 SQL 样本，不能据此宣称业务对账通过。

测试发现当前 Prisma 交互事务在 COMMIT 阶段可能未将延迟约束失败返回给调用方。生产事务回调结束前显式执行 `SET CONSTRAINTS ALL IMMEDIATE`；真实反例确认失败时 assignment 和幂等成功缓存都回滚，接口不能误报成功。纯函数、单元测试与真实数据库均保留此回归。

`checkInventoryAllocationConcurrency.ts` 在 `aerolink_allocation_test_integration_20260909` 验证：

1. 库存 10 件并发预留 6+6，仅一个成功；释放后 4+4 经有限重试都可提交。
2. 序号件并发预留只有一个活动分配；同幂等键只有一组来源、事件和响应。
3. 成交显式分配 4 件后，修订释放剩余未分配的 6 件，保留订单 4 件。
4. 独立质量复核、陈旧附件/实物快照、已消费审核均按规则拦截；旧商业版次的既有订单仍可出库。
5. 消费与释放竞争只有一个合法结果，在手量、父子计数、行投影一致。
6. 到期清理以 `limit=1` 分页，耗尽记录不阻塞后续；订单 3 件与未来到期 2 件保留，重复运行不增加事件。
7. 实际出库的序号补回数量后仍不能再次预留；试图清空序号并改成批次追踪被拒绝，历史身份保留。

最后只读对账（同一集成库累计独立合成样本）：22 个库存明细、38 个父分配、12 个子分配、38 条报价行、12 条订单行、98 个事件、12 条 OUTBOUND；`PASS`、`issues=[]`。这不代表真实历史数据已经迁移或通过验收。

后续真实反例还模拟了普通幂等缓存被清理：原预留已经转入订单后，使用原始命令重放仍识别为同一预留，不新增父记录或重复占用。
