# D13 多批发运、签收与退货实施设计

日期：2026-09-09。状态：代码核对和数量纯函数增量完成，数据库及业务命令待实施；D12 的数量分配及出库事实为前置依赖。本文是下一步待办，不是完整业务验收记录。

## 已确认的缺口

现有 `ShipmentTracking.orderId` 唯一，一张订单只能对应一个追踪记录；订单头运单字段不能表达多个发运批次。D12 已支持同一订单行的多个库存分配和分次消费，但尚未把每次出库对应到运单、签收或退货。现有发运追踪主要是读取接口，不能作为实际交付数量的权威来源。

## 实施顺序

1. 建立现代发运头、发运行及不可改写的事件。发运行明确引用订单行、Assignment 和实际 OUTBOUND 流水；同一流水可拆到多个运单，但累计不能超过该流水实际出库数量。运单不能再次扣库存。旧追踪记录保留原语义，不能自动转成已验证的现代发运量。
2. 发运命令逐项校验实际出库链路和交付文件，保存当时的文件身份及哈希。每批独立运单和承运人，使用幂等键、Serializable 事务及当前对象权限。历史绑定、初始数量和证据不能通过普通 PATCH 改写。
3. 签收按发运行累加，支持部分签收；签收不能超发运量。订单已发量继续来自 D12 的实际消费，已签收量来自签收明细；只有全部订单行足量签收才能进入已交付状态。物流状态文本不能代替数量判断。
4. 退货必须引用原发运行，累计接收不能超过原发运数量；允许未签收拒收后退回，不能为退货先伪造客户签收。收回件先进入独立待检/隔离保管记录，可售余额不增加；记录接收人、实物身份、数量和证据。独立质量人员核对后，使用受控放行命令转入库存，并写入关联原出库的 RETURN 流水。历史分配与消费计数不倒退。
5. 序号件复售只接受可追溯到最近一次出库的受控退货放行；修改数量、AVAILABLE 状态、件号或序号均不能替代该授权。批次退货的待检数量与既有可售库存分别核算，不能把整批未检查退货直接混入可售数量。
6. 订单页展示所有发运批次及累计量，提供按实际来源选择、创建运单、签收和退货待检入口；质量页/订单面板提供独立放行。客户价格和采购成本不进入物流、质量响应。

## 必须通过的验收

- 同一订单两次发运、两个运单；同一订单行由两个库存批次交付，累计数量正确。
- 同一 OUTBOUND 流水拆分运单后的累计量守恒，并发绑定和幂等重放不重复占用。
- 部分出库、部分签收不会显示整单交付完成；物流状态不能越过数量约束。
- 发运文件必须属于实际订单或实物来源；无关文件、失效证据和越权对象被拒绝。
- 退货接收不增加可售量；重复接收、超量退货、收货人自批和无证据放行被拒绝。
- 序号件经过出库、受控退货和独立放行后可以合法再次分配；第二次出库后，第一次退货授权不能重用。
- 真实 PostgreSQL 并发及数量对账、真实 HTTP 流程和两个岗位的浏览器操作通过；旧追踪读取兼容且不伪造历史映射。

全部工作在本地完成。真实历史追踪数据的映射与生产迁移仍需单独证据；不通过自动回填推断历史运单、签收或质量授权。

## 实施时需封闭的旁路

普通库存创建、明细 PATCH、删除及旧预留/释放/出库命令不能接受退货来源或代替质量放行。序号件的再次销售校验须同时覆盖现代和旧入口，不能只在新分配接口检查。退货隔离是独立保管数量，不增加原明细 `quantity`；批次中原本已有的合格库存也不应仅因存在部分待检退货而整批停用。对原明细手工增量、身份改写或来源删除的保护应在服务层落实，结合事务及历史外键，不能只依赖前端隐藏按钮。

当前 `FulfillmentReview` 是出库复核，不能复用成退货放行记录。序号放行记录必须引用具体原 OUTBOUND，且后续再次出库后不能重用旧放行。批次放行时身份、条件、仓位与来源不匹配应拒绝合并或进入独立受控明细，不能静默改写 D12 历史身份。
