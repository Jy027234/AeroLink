## 页面崩溃

在实际试用环境以当前已登录管理员点击“系统设置 → Webhooks”，异步加载后出现 `Cannot read properties of undefined (reading 'map')`。不是账号权限或外部平台配置问题。

`GET /api/webhooks/phase2/replay` 返回 `{ data: batches, pagination }`。`listReplayBatches` 原来使用会自动提取 `data` 的 `request`，调用页面却继续读取 `result.data`，将回放批次数组置为 undefined，导致渲染崩溃。

修复候选 `e8c7b7a77ead5693a66607f2083d89a40bf7417f` 将该接口改为既有 `requestEnvelope`，保留列表与分页结构。没有使用空数组兜底掩盖契约错误，没有改后端、业务规则或数据库迁移。

新增回归覆盖空批次、有数据及非零 offset/total、401 刷新后保留响应结构。定向客户端与会话测试 2 文件 / 9 项通过；本机 Vitest 4.1.5，TypeScript 构建检查通过。后续远程测试按锁文件安装，证据分别记录。

## 当前能否提醒微信或飞书用户

当前未完成企业微信或飞书的端到端提醒接入。

- Settings 的 Webhooks 面板主要管理入站端点、投递/审计及失败重试、回放。入站是外部系统向 AeroLink 发数据，不是向群聊发送提醒。
- 服务端 `webhookService.ts` 有真实 HTTP 发送、事件订阅和失败重试；Worker 会处理待投递消息。这条通用出站机制发送 AeroLink 事件 envelope，需要接收方处理，不等于平台机器人消息适配。
- `notificationPreferences.ts` 保存 `wechatNotify` / `larkNotify`，`channelBindings.ts` 保存用户渠道配置；仓库未找到消费这些偏好并完成平台消息发送的适配器。保存成功不表示消息送达。
- 前端虽定义 `/im/sendWechat`、`/im/sendLark`，后端没有对应 `/im` 路由；通知分发路由实际写入站内 Notification，渠道为 SYSTEM。不能将这些前端方法当成可用外发能力。
- 个人微信与企业微信是不同目标；现有“企业微信通知”开关不能作为个人微信已接通的证明。当前也没有向真实微信或飞书发送测试消息的验收证据。

平台格式也不相同：[企业微信群机器人](https://developer.work.weixin.qq.com/document/path/91770)使用 `msgtype/text.content`，[飞书机器人](https://www.feishu.cn/content/7271149634339422210)使用 `msg_type/content.text`；当前通用事件 envelope 没有这些转换。通用投递目前只按 HTTP 成功状态判定，不解析平台响应体中的业务错误码。因此不能把“填了机器人 URL”或 HTTP 200 视为已送达；若经外部中转，需要由中转实现格式转换与平台结果校验。

相关实现：`src/api/client.ts`、`src/sections/Settings/WebhookManagementPanel.tsx`、`server/src/routes/webhooks-phase2.ts`、`server/src/lib/webhookService.ts`、`server/src/worker.ts`、`server/src/routes/notificationPreferences.ts`、`server/src/routes/channelBindings.ts`。

## 后续接入的验收要求

先选定企业微信或飞书，以及群提醒或指定员工提醒；按该平台接入消息格式、凭据/签名、收件目标、权限范围和响应错误码，再把业务事件与通知偏好接起来。用平台实际成功响应及用户确实收到的样本验收，失败重试和日志须能追踪。实际外发测试须有明确目标和授权，本轮未发送业务或测试消息给外部人员。

这是已识别的渠道接入缺口，不因为修复 Webhooks 页面就视为完成，也不扩大成本次崩溃修复中的新集成开发。
