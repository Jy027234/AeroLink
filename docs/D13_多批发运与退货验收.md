# D13 多批发运与退货验收

日期：2026-09-09。状态：本地实现与隔离测试验收通过。D14 采购及结算、D15–D18 等后续目标仍未完成；本文不代表生产迁移或正式业务放行。

## 已实现行为

- `Shipment`、`ShipmentLine`、`ShipmentEvent` 表达独立承运人、运单和实际发运切片。一条发运行明确引用订单行、Assignment、实际负数 OUTBOUND 及其已消费质量复核，累计不能超出原出库数量；创建发运不再次扣库存。
- `InventoryTransaction.fulfillmentReviewId` 保存实际消费的审核 ID。历史未绑定记录显示待人工核实且不可自动发运，不按日期、数量或“最近一次审核”推断来源。
- 签收独立按行累加，部分签收保留未交付数量。只有全部订单行足量签收，且已出库数量相符，才转为已交付。现代订单普通状态接口不能代替签收；取消、已交付、已完成订单不能追加新的签收命令。
- `ReturnHold` 记录原发运行、实物身份、接收人和证据。允许未签收拒收后退回；待检数量不计入可售库存，历史出库及客户签收计数不倒退。
- 独立质量放行核对身份、证书、剩余寿命、客户要求和当前隔离记录快照，写入唯一正数 RETURN。默认禁止经办人自批，管理员也不能跳过。放行使用当前上下文指纹，接收时指纹保留为审计事实。
- 序号件再次分配要求每条历史 OUTBOUND 都有唯一对应的受控放行及 RETURN；新退货对应唯一尚未归还的 OUTBOUND。毫秒时间相同或 UUID 排序不能改变判断；第二次出库后第一次退货授权不可重用。
- 批次待检退货与原可售余额分别核算，现有正常库存仍可分配。退货放行保留其活动分配量；已有其他隔离库存的明细不能被本次放行整体改为可售。序号件入库前数量和分配必须均为零。
- 签收及退货新附件必须由提交人本人上传。首次使用通过 CAS 绑定订单并递增版本，禁止跨订单改绑；历史接收证据按订单及精确版本/哈希读取。质量人员可下载实际退货接收证据，不因拥有质量权限而获得其他订单附件访问权。
- 订单页面提供实际出库来源选择、多运单、部分签收、退货隔离及独立放行。质量上下文显示身份、库存/分配、证书状态/有效期、寿命和接收证据下载。响应不包含客户价格、采购成本或毛利。
- 六个业务接口均进入现有权限、审计、幂等及事务体系。写操作使用 Serializable 和提交前 deferred 约束检查，永久命令保留规范化请求指纹；响应缓存重放前后重新检查当前对象权限。

## 数据库验证

本机 PostgreSQL 16 隔离容器 `aerolink-review-test-20260908`，Node 22.23.2 / npm 10.9.8。两条新增迁移为 `20260909000100_shipments_and_return_holds` 和 `20260909000200_shipment_projection_guards`，共 27 条迁移。第二条是向前补强迁移，没有修改已应用的第一条。

数据库限制不可改写的来源、初始数量和事件，签收量等于签收事件之和、退货量等于隔离记录之和，放行必须对应实际 RETURN。发运状态限定为三种现代状态并与签收量一致；质量复核数量必须等于 OUTBOUND 的绝对值。延迟检查允许同一事务先更新行再更新头状态。

- `checkShipmentDatabaseInvariants.ts`：合法发运、签收、隔离及放行通过；超量、事件删除、来源替换、审核数量不符、伪造已交付和非法状态反例均被拒绝。
- `checkShipmentSerialReentry.ts`：真实服务链完成出库 → 未签收退回 → 隔离 → 独立放行 → 再次销售出库。旧命令重放不恢复数量；手工补回数量后仍不能重用旧授权。末次样本 `fff951dc`，2 条 OUTBOUND、1 条 RETURN。
- `checkShipmentReconciliation.ts`：HTTP/UI 库核对 7 个发运、9 条发运行、10 条现代 OUTBOUND、10 个现代订单、4 个退货记录，`PASS`、差异为空。序号服务库核对 3 个发运、3 条发运行、5 条 OUTBOUND、5 个现代订单、3 个退货记录，`PASS`、差异为空。累计包含本批早期隔离样本，不将它们表述为真实历史数据。

首次 SQL 验证发现 PL/pgSQL 大小写字段引用及 SELECT/INTO 对齐错误，已在首条迁移首次稳定前修正并重建两个根测试库；后续补强使用独立新迁移。Prisma 5.22.0 客户端在隔离目录生成并核对 DMMF，已存在且被其他服务占用的引擎 DLL 没有替换或强行解锁。
