# D10 多行交易模型最小可迁移实施设计

日期：2026-09-08\
范围：只读核对当前 Prisma 模型和服务入口；本轮不修改 schema、迁移或业务代码。

## 1. 当前数据关系与入口

当前系统实际上把 RFQ、供应商报价、客户报价单和订单都当成“一行单据”。Inquiry 已有 InquiryItem 数组，但没有保存它来自哪个 RFQ，导致多行链路在询价入口被截断。

| 对象 | 当前 Prisma 关系与字段事实 | 当前服务入口及影响 |
| --- | --- | --- |
| RFQ（schema.prisma:579） | rfqs 有 customerId、createdBy、partNumber、quantity、uom、conditionCode、requiredDate、targetPrice 等单行字段；有 quotations[] 和 supplierQuotes[]，没有 RFQ 行表，也没有 Inquiry 关系。 | POST /api/rfqs（routes/rfqs.ts:360）按单行创建；GET /api/rfqs/:id（:326）只返回单行并附报价单摘要。 |
| Inquiry（schema.prisma:620） | inquiries 只有 supplierId、isAOG、status、sentAt；有 items[] 和 supplierQuotes[]，没有 rfqId。 | POST /api/inquiries（routes/inquiries.ts:88）接收 rfqId，但只用它读取一个 RFQ，再为每个 supplier 创建一个 Inquiry 和一个 InquiryItem，源 RFQ ID 没有落库。 |
| InquiryItem（schema.prisma:636） | inquiry_items 只有 inquiryId、partNumber、quantity、requiredDate、certificateRequired；只有 Inquiry 外键，没有 RFQ 行或 SupplierQuote 外键。 | Inquiry 序列化（routes/inquiries.ts:11）返回 items，但没有 item ID 和源行 ID，后续无法安全定位一条需求。 |
| SupplierQuote（schema.prisma:649） | supplier_quotes 的 partNumber、quantity、unitPrice、totalPrice 本身就是一行；rfqId 和 inquiryId 都可空，且没有 rfqLineId/inquiryItemId；金额已有 Decimal shadow。 | GET/POST/compare/select-winner（routes/supplierQuotes.ts:88、193、322、462）允许按 RFQ 或 Inquiry 聚合，创建时客户端可直接提交 partNumber/quantity；select-winner 会清除同 rfqId + inquiryId 下所有行的 isWinner。 |
| Quotation（schema.prisma:702） | quotations 有 rfqId、customerId、partNumber、quantity、unitPrice、costPrice、totalPrice、margin 等单行字段；有 orders[]，但 Order.quotationId 当前带 @unique，因此实际是一对一；orderId/orderNumber 是冗余字符串，没有外键。 | POST /api/quotations（routes/quotations.ts:659）和 createQuotationAggregate（modules/quotationOrder/service.ts:108）只接受一组单价、成本、数量；submit/approve/send/accept 都以 quotationId 为边界。 |
| Order（schema.prisma:827） | orders 有唯一 quotationId、partNumber、quantity、totalAmount 以及库存和出库字段；没有订单行。outboundQuantity 只在订单头上，无法区分多个件号。 | POST /api/orders（routes/orders.ts:552）和 createOrderFromQuotation（service.ts:991）从整张 Quotation 复制一行；质量审核、库存事务和运输入口当前主要只接 orderId。 |

现有 RFQ、Quotation、Order 的 scope 也按这些头表字段判断 owner 和 department。多行改造应保留头表作为权限和聚合边界，新增行 ID 只用于校验“该行属于该头单据”，不能由客户端单独指定跨单据的 partNumber 或 quantity。

## 2. 设计取舍

1. 采用新增行表加可空关联字段的增量迁移。现有单行列在兼容窗口内保留并继续双写，避免一次迁移同时改动所有报告、PDF 和前端类型。
2. 不使用一个同时指向 RFQ、Inquiry、Quotation、Order 的多态 lineId。每条关系使用明确的 rfqLineId、inquiryItemId、quotationLineId、orderLineId，数据库外键和服务校验才有明确边界。
3. 新的多行请求必须提交服务端已经返回的行 ID。客户端提交的 partNumber、quantity、totalPrice 只能作为旧单行请求的兼容字段，不能覆盖已定位行的事实。
4. 新行金额使用 PostgreSQL Decimal(18,4) 作为唯一账务来源。旧 Float 列继续作为兼容投影，读取时沿用 Decimal shadow 优先规则。
5. 目前首期币种政策只允许 USD。行级 currency 仍然落库，禁止把不同币种直接相加；以后增加汇率时另加汇率快照和换算金额。

## 3. Prisma 最小变更

下面是目标字段清单，不是本轮要直接粘贴进 schema.prisma 的代码。字段名以现有 camelCase 约定为准。

### 3.1 新增 RfqLine

新增 RfqLine（数据库表 rfq_lines），保留 RFQ 头表的客户、经办人、紧急度和整体状态，以下字段从 RFQ 行级化：

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| id | String 主键，uuid | 所有后续 InquiryItem、SupplierQuote、QuotationLine 的源 ID。 |
| rfqId | String，必填，FK RFQ，onDelete Cascade | 一条 RFQ 可有多行。 |
| lineNo | Int，必填 | 从 1 开始；unique(rfqId, lineNo)。 |
| partNumber | String，必填 | 需求件号快照。 |
| quantity | Int，必填，CHECK > 0 | 需求数量。 |
| uom | String，默认 EA | 数量单位。 |
| conditionCode | String，默认 NE | 件号条件。 |
| description | String 可空 | 行描述。 |
| serialNumber / batchNumber | String 可空 | 行级序列号或批次约束。 |
| alternatePartNumbers | String 可空 | 沿用当前 JSON 字符串兼容格式；后续再结构化。 |
| certificateRequired / certificateType | Boolean / String 可空 | 行级证书要求。 |
| requiredDate | DateTime | 行级交付日期。 |
| leadTimeDays | Int 可空 | 行级交期要求。 |
| targetPriceDecimal | Decimal(18,4) 可空 | 行级目标价；RFQ 旧 targetPrice 保留为投影。 |
| targetPriceCurrency | String，默认 USD | 目标价币种。 |
| status | String，默认 OPEN | 行级取消或关闭；用 SQL CHECK 限定 OPEN/CANCELLED/COMPLETED。 |
| createdAt / updatedAt | DateTime | 审计时间。 |

RFQ 增加 lines RfqLine[] 和可选 inquiries Inquiry[] 反向关系。RFQ 现有 partNumber、quantity 等列暂不删除，继续作为兼容投影。

### 3.2 补齐 Inquiry 和 InquiryItem

Inquiry 增加：

~~~text
rfqId String?
rfq RFQ? @relation(fields: [rfqId], references: [id], onDelete: SetNull)
~~~

并增加 index(rfqId, supplierId)。历史 Inquiry 可能无法唯一推断源 RFQ，因此 rfqId 必须可空。

InquiryItem 增加：

~~~text
lineNo Int @default(1)
rfqLineId String?
rfqLine RfqLine? @relation(fields: [rfqLineId], references: [id], onDelete: SetNull)
~~~

增加 index(rfqLineId) 和 unique(inquiryId, lineNo)。保留现有 partNumber、quantity、requiredDate、certificateRequired，供无源 RFQ 的历史询价继续读取。新入口必须由 rfqLineId 复制这些值，而不是接受任意件号和数量。

### 3.3 补齐 SupplierQuote 的源行

SupplierQuote 增加：

~~~text
rfqLineId String?
inquiryItemId String?
currency String @default("USD")
rfqLine RfqLine? @relation(fields: [rfqLineId], references: [id], onDelete: SetNull)
inquiryItem InquiryItem? @relation(fields: [inquiryItemId], references: [id], onDelete: SetNull)
~~~

保留已有 rfqId、inquiryId 和单行金额字段，增加 index(rfqLineId, supplierId, status) 及 index(inquiryItemId, supplierId, status)。历史孤立报价允许两个新关联都为空，但新建报价必须至少关联 inquiryItemId 或 rfqLineId 之一。

如果两个关联同时存在，服务事务必须校验：

- inquiryItem.inquiryId 等于 SupplierQuote.inquiryId；
- inquiryItem.rfqLineId 等于 SupplierQuote.rfqLineId；
- Inquiry.supplierId 等于 SupplierQuote.supplierId；
- rfqLine.rfqId 等于 SupplierQuote.rfqId。

这些跨行约束不能只靠普通 Prisma relation 表达，应在服务层事务中校验，并在迁移后的质量脚本中持续检查。不要把 isWinner 设计成整张 RFQ 的唯一 winner；winner 应限定在同一个 rfqLineId（或同一个 inquiryItemId）和供应商询价轮次内。

### 3.4 新增 QuotationLine

新增 QuotationLine（数据库表 quotation_lines）：

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| id | String 主键，uuid | 客户报价行 ID。 |
| quotationId | String，必填，FK Quotation，onDelete Cascade | 报价单头。 |
| lineNo | Int，必填 | unique(quotationId, lineNo)。 |
| rfqLineId | String，必填，FK RfqLine，onDelete Restrict | 必须属于 quotation.rfqId。 |
| sourceSupplierQuoteId | String 可空，FK SupplierQuote，onDelete SetNull | 选中的供应商报价来源；人工定价可为空。 |
| partNumber / description / uom | String / String? / String | 从 RFQLine 复制的不可变报价快照。 |
| quantity | Int，CHECK > 0 | 对客户承诺的报价数量，不得超过 RFQLine.quantity。 |
| unitPrice / costPrice / lineTotal | Decimal(18,4) | unitPrice、costPrice 乘 quantity 后得到 lineTotal 和成本总额。 |
| marginAmount / marginPercent | Decimal(18,4) / Decimal(9,4) | 行毛利金额与百分比；百分比不使用 Float。 |
| currency | String，默认 USD | 行币种，首期必须与 Quotation.currency 相同。 |
| status | String，默认 DRAFT | DRAFT/PENDING_APPROVAL/APPROVED/PARTIALLY_ACCEPTED/ACCEPTED/REJECTED/CANCELLED。 |
| acceptedQuantity | Int，默认 0 | 已成交数量，累计不超过 quantity。 |
| reservedQuantity | Int，默认 0 | 已预留数量，累计不超过 quantity。 |
| inventoryDetailId / serialNumber / batchNumber | 可空 | 仍可保留单行库存绑定，行化后按行迁移。 |
| createdAt / updatedAt | DateTime | 审计时间。 |

Quotation 增加 lines QuotationLine[]。Quotation 现有 totalPrice、costPrice、margin、partNumber、quantity 等列保留为兼容投影；报价单头 rfqId/customerId/createdBy 继续作为权限和聚合键。

### 3.5 新增 OrderLine

新增 OrderLine（数据库表 order_lines）：

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| id | String 主键，uuid | 订单行 ID。 |
| orderId | String，必填，FK Order，onDelete Cascade | 订单头。 |
| lineNo | Int，必填 | unique(orderId, lineNo)。 |
| quotationLineId | String，必填，FK QuotationLine，onDelete Restrict | 订单行必须追溯到客户报价行。 |
| partNumber / uom | String / String | 订单行快照。 |
| quantity | Int，CHECK > 0 | 本次成交数量。 |
| unitPrice / lineTotal / currency | Decimal(18,4) / Decimal(18,4) / String | 订单金额快照，不随报价单后续展示变动。 |
| outboundQuantity | Int，默认 0 | 当前行已出库数量。 |
| outboundStatus | String，默认 PENDING | PENDING/PARTIAL/COMPLETED。 |
| inventoryDetailId / serialNumber / batchNumber | 可空 | 行级实物绑定。 |
| createdAt / updatedAt | DateTime | 审计时间。 |

Order 增加 lines OrderLine[]。为支持同一报价单多次部分成交，移除 Order.quotationId 的 @unique，改为 index(quotationId)；现有数据仍保持一对一，不会因删除唯一约束而自动产生重复订单。Quotation.orderId/orderNumber 暂保留为“最新/兼容订单”投影，不再把它们当成关系来源。

如果业务决定只允许一次部分成交并在同一个订单中追加行，可以暂时保留唯一约束；但“多次部分成交、多个订单”一旦成为需求，就必须采用上面的非唯一 quotationId，并在事务中按 QuotationLine 汇总已有 OrderLine 数量防止超卖。

## 4. 兼容一行迁移顺序

### M0：预检和报告

在生产库只读执行以下检查，保存计数和异常 ID：

1. 每个 RFQ、Quotation、Order 的数量、件号、日期和 Decimal shadow 是否有效。
2. Quotation.rfqId 是否都有对应 RFQ；Order.quotationId 是否都有对应 Quotation。
3. 已有 Order.quantity 与对应 Quotation.quantity 是否不一致。
4. InquiryItem 是否能按 supplier、partNumber、quantity、requiredDate、certificateRequired 唯一匹配某个 RFQ；SupplierQuote 的 rfqId/inquiryId 是否互相一致。
5. SupplierQuote.totalPriceDecimal 是否等于 unitPriceDecimal 乘 quantity（按 4 位小数舍入）。

预检只生成报告，不因为“最像”的件号和数量强行建立关联。

### M1：先加表和可空关系

按 RFQLine、Inquiry 关联、InquiryItem 关联、SupplierQuote 关联、QuotationLine、OrderLine 的顺序生成一个前向迁移：

- 先建三张新表、索引和行级数量/金额 CHECK；
- 再加 Inquiry.rfqId、InquiryItem.rfqLineId、SupplierQuote.rfqLineId/inquiryItemId/currency；
- 新外键对历史可空关联使用 SetNull，对已经有行事实的 QuotationLine/OrderLine 使用 Restrict；
- 在这一步不要删除 RFQ、Quotation、Order 的旧列，也不要立刻删除 quotationId 唯一约束，先完成回填和回归。

### M2：每个 RFQ 生成兼容行 1

对每个现有 RFQ 插入一条 RfqLine：

- lineNo=1；
- 复制 partNumber、quantity、uom、conditionCode、description、序列号/批次、证书、requiredDate、leadTimeDays；
- targetPriceDecimal 使用已有 targetPrice 四舍五入到 4 位；
- RfqLine 的状态映射 RFQ 头状态：非 CANCELLED 为 OPEN，已取消为 CANCELLED；
- 使用迁移脚本生成 uuid，不依赖数据库安装了某个 UUID 扩展。

回填后检查 RFQ 数量与 RfqLine 数量是否相等，并检查每个 RFQ 恰好存在 lineNo=1。

### M3：回填 Inquiry 和 SupplierQuote 的关联

1. Inquiry.rfqId：优先使用未来写入的关系。历史 Inquiry 没有源列，只能在其恰好有一个 Item 且 Item 五个字段与某个 RFQ 唯一匹配时回填；零个或多个候选均保持 NULL，并写入待人工确认报告。
2. InquiryItem.rfqLineId：仅在 Inquiry.rfqId 已确定且 Item 字段与该 RFQ 的唯一 RfqLine 匹配时回填。
3. SupplierQuote.inquiryItemId：若 inquiryId 下恰好只有一个 Item，且件号/数量一致则回填；多行或冲突项保持 NULL。
4. SupplierQuote.rfqLineId：若 rfqId 对应唯一 lineNo=1 且件号/数量一致则回填。若 quote 同时有 Inquiry 和 RFQ 关系，先检查两条路径指向同一行。
5. 任何无法确定的历史报价都保留旧 rfqId/inquiryId 和旧行字段，标记 legacy_unlinked；新多行接口不接受这类记录作为 sourceSupplierQuoteId。

### M4：回填 QuotationLine 和 OrderLine

1. 每个现有 Quotation 按其 rfqId 找到 RfqLine lineNo=1，插入一个 QuotationLine。
2. 复制 Quotation 的 partNumber、quantity、unitPriceDecimal、costPriceDecimal、totalPriceDecimal、currency 和库存绑定。没有 Decimal shadow 时从 Float 按 4 位舍入。
3. lineTotal 必须以 unitPriceDecimal 乘 quantity 重新计算；若与旧 totalPriceDecimal 不一致，保留旧值到迁移异常报告，不静默覆盖。
4. quotationLine.status 映射头状态。acceptedQuantity 不凭头状态猜测：有旧订单时取对应订单数量，没有订单时为 0 并把“已接受但无订单”列为需复核数据。
5. 每个现有 Order 按 quotationId 找到唯一 QuotationLine，插入一个 OrderLine，复制订单实际 quantity 和金额快照。若订单金额与报价行金额不一致，保留订单事实并报告差异。
6. 所有旧单据完成一行回填且异常已出报告后，才允许把新入口切到行 ID。

### M5：约束、双写和开关

- 新写入始终在同一个事务创建头和行，并同步更新旧头字段的兼容投影。
- 旧单行 API 在请求没有 lines 时生成一条行；当 RFQ/Quotation 有多行而请求仍使用旧的 partNumber/quantity 时返回 409，要求客户端提交行 ID，不能默认选择第一行。
- 通过 feature flag（例如 MULTI_LINE_TRANSACTIONS=false）先只读返回 lines，再开启多行写入。
- 观察至少一个完整业务周期后，若要支持重复部分成交，再移除 Order.quotationId 唯一约束并增加并发汇总校验。

## 5. 部分报价和部分成交的 ID 传递

### 5.1 RFQ 到 Inquiry

新的 RFQ 创建请求在现有头字段之外增加 lines 数组。服务端为每一行生成 rfqLineId，响应同时返回 rfqId 和 lines[].id。旧请求没有 lines 时把现有单行字段包装为 lineNo=1。

Inquiry 创建请求建议为：

~~~json
{
  "rfqId": "rfq-id",
  "lineIds": ["rfq-line-id-1", "rfq-line-id-2"],
  "supplierIds": ["supplier-id"]
}
~~~

服务端检查所有 lineIds 属于 rfqId，然后为每个 supplier 创建一个 Inquiry（保存 rfqId）和对应 InquiryItem（保存 rfqLineId）。响应返回 inquiryId、items[].id 和 items[].rfqLineId，后续供应商报价只引用 InquiryItem ID。

### 5.2 Inquiry 到 SupplierQuote

供应商报价新请求二选一：

~~~json
{
  "inquiryItemId": "inquiry-item-id",
  "supplierId": "supplier-id",
  "quantity": 3,
  "unitPrice": "125.5000",
  "leadTimeDays": 7
}
~~~

或直接报价：

~~~json
{
  "rfqLineId": "rfq-line-id",
  "supplierId": "supplier-id",
  "quantity": 3,
  "unitPrice": "125.5000",
  "leadTimeDays": 7
}
~~~

服务端从关联行读取件号、需求数量和条件，验证 quote quantity 不超过需求数量，计算 totalPriceDecimal，不接受客户端的 totalPrice 作为事实。由 InquiryItem 进入时同时写入 rfqLineId/rfqId/inquiryId；旧的无行报价继续可读但不能参与新的多行选择。

### 5.3 RFQ/SupplierQuote 到 Quotation

Quotation 创建请求增加 lines，每行至少有 rfqLineId、quantity、unitPrice、costPrice，可选 sourceSupplierQuoteId：

~~~json
{
  "rfqId": "rfq-id",
  "lines": [
    {
      "rfqLineId": "rfq-line-id-1",
      "sourceSupplierQuoteId": "supplier-quote-id",
      "quantity": 2,
      "unitPrice": "130.0000",
      "costPrice": "100.0000"
    }
  ]
}
~~~

服务端验证行属于同一 RFQ，SupplierQuote 的 source 行相同且供应商报价状态可用，然后生成 quotationLineId。部分报价就是只选择部分 rfqLineId，或选择某行小于需求量的 quantity；未报价数量留在 RfqLine 的可用数量中。Quotation 头的 totalPriceDecimal 等于所有 QuotationLine.lineTotal 之和。

### 5.4 Quotation 到 Order

客户确认或直接创建订单时提交：

~~~json
{
  "quotationId": "quotation-id",
  "lines": [
    { "quotationLineId": "quotation-line-id-1", "quantity": 2 }
  ]
}
~~~

服务端在同一事务中锁定待成交的 QuotationLine，计算已有 OrderLine.quantity 总和，确保已有成交量加本次 quantity 不超过报价量；然后创建 Order 和 OrderLine，并返回 orderId、orderLineId、quotationLineId、成交 quantity。QuotationLine.acceptedQuantity 累计更新，状态可为 PARTIALLY_ACCEPTED 或 ACCEPTED。

如果允许同一报价后续再次部分成交，Order.quotationId 必须非唯一，响应使用 orders[]；如果产品只允许一张订单，则后续成交追加到同一个 Order，并且 orderLineId 仍必须返回给库存和出库流程。两种模式都不能只传 quotationId 加一个头 quantity。

### 5.5 交付和库存继续传行 ID

当前质量审核、库存事务和运输接口多以 orderId 加 quantity 为参数。多行启用后，以下入口必须增加 orderLineId，并在服务层验证它属于 orderId：

- quality-review 预览和提交；
- inventory transaction 出库、预留和释放；
- shipment tracking 的实际发运记录；
- 订单 PDF/邮件中的行列表。

单行旧请求可以在订单恰好一行时由 orderId 自动解析；订单有多行时缺少 orderLineId 必须返回 409，避免把一个件号的数量扣到另一个件号。

## 6. 金额和数量对账口径

### 6.1 唯一计算来源

所有新行金额按 Decimal(18,4) 计算，使用现有 normalizeMoney 的四位小数和 ROUND_HALF_UP 规则。客户端提交 totalPrice、margin 或 header total 只用于显示校验，服务端必须重新计算：

| 层级 | 对账公式 | 允许的兼容投影 |
| --- | --- | --- |
| RFQLine | quantity 是需求量；targetPrice 只是需求参考，不计入收入。 | RFQ.quantity 是所有行 quantity 的合计；RFQ.partNumber 为第一行显示值，并标记为兼容字段。 |
| SupplierQuote | totalPrice = round(unitPrice × quantity, 4)。 | 旧 Float totalPrice/unitPrice 与 Decimal shadow 保留，读取 Decimal 优先。 |
| QuotationLine | lineTotal = round(unitPrice × quantity, 4)；costTotal = round(costPrice × quantity, 4)；marginAmount = lineTotal - costTotal。 | Quotation.totalPriceDecimal = sum(lineTotal)；costPrice 为总成本或第一行的旧投影必须在 API 文档中区分。 |
| Quotation 头 | totalPriceDecimal = Σ QuotationLine.lineTotal；costTotal = Σ QuotationLine.costTotal；marginPercent = (totalPriceDecimal - costTotal) / totalPriceDecimal × 100。 | 旧 margin 改为加权总毛利率，不能平均各行百分比。 |
| OrderLine | lineTotal = round(unitPrice × 成交 quantity, 4)，unitPrice 从 QuotationLine 快照。 | Order.totalAmountDecimal = Σ OrderLine.lineTotal；Order.quantity = Σ 行数量。 |
| 部分成交 | remaining = QuotationLine.quantity - acceptedQuantity；所有 OrderLine.quantity 总和不得超过 QuotationLine.quantity。 | Quotation.acceptedAt/Order 状态仍是头级流程投影，不能替代数量对账。 |

当前 Order 的 importDuty、vatAmount、totalLandCost、exchangeCoreCharge 是独立的物流/税费字段。第一阶段把 totalAmount 定义为商品行金额合计，税费和落地成本单独对账；如果要展示含税/落地总额，应新增明确的 landedTotalDecimal 或费用行，不能把税费静默加到 totalAmount。

所有聚合必须按 currency 分组。首期 API 强制 USD；跨币种报价不能参与 compare、Quotation 合计或 Order 合计。未来汇率换算需要保存 rate、rateAsOf 和 source，不能用当前汇率回算历史订单。

### 6.2 必须持续检查的差异

迁移后增加只读 reconciliation 检查，至少报告：

1. RfqLine.quantity <= 0 或同一 RFQ 的 lineNo 重复。
2. SupplierQuote.totalPriceDecimal 与 unitPriceDecimal × quantity 不一致。
3. QuotationLine.rfqLineId 不属于 Quotation.rfqId。
4. Quotation.totalPriceDecimal 与行合计不一致。
5. QuotationLine.acceptedQuantity、reservedQuantity 超过 quantity。
6. OrderLine.quotationLineId 不属于 Order.quotationId 对应报价。
7. 同一 QuotationLine 的 OrderLine 数量合计超过报价量。
8. Order.totalAmountDecimal 与 OrderLine 合计不一致，或订单币种不一致。
9. 旧头字段与行投影不一致。差异进入报告，不能用触发器静默覆盖历史事实。

## 7. 服务入口改造顺序

1. 先改 repository/select/include 和 serializer，让 GET 端点在单行情况下返回 lines，验证旧前端字段完全不变。
2. 改 RFQ 和 Inquiry 创建：单行请求生成 RfqLine，Inquiry 持久化 rfqId，响应返回行 ID。
3. 改 SupplierQuote 创建、比较和中选：按行过滤和中选，客户端不再决定件号/数量。
4. 改 Quotation 创建、审批、发送和 PDF：审批快照、邮件和 PDF 遍历 QuotationLine；现有审批金额改为头行合计。
5. 改 accept/order 创建：按 QuotationLine 接受数量，生成 OrderLine，使用行级并发检查。
6. 改库存、质量、出库和运输入口：多行订单强制 orderLineId；保持单行 orderId 兼容解析。
7. 改报告、CSV、Socket change hint 和前端类型。Socket 只传 rfqLineId/quotationLineId/orderLineId、状态和版本，金额重新走当前授权 HTTP 查询。

## 8. 回归验收

最低测试矩阵：

- 现有单行 RFQ → 一个 InquiryItem → 一个 SupplierQuote → 一个 QuotationLine → 一个 OrderLine，所有旧 API 响应和 Decimal 合计保持一致。
- 两行 RFQ 只询价其中一行时，Inquiry 只包含选定 rfqLineId；另一行不能出现在 SupplierQuote compare。
- 两行 RFQ 对同一件号分别收到两家供应商报价时，中选只影响该行，不清除另一行 winner。
- Quotation 只报价一行或把一行数量从 10 报到 4 时，头合计、行 ID 和剩余数量正确。
- 同一报价先成交 3 再成交 2 时，OrderLine 数量合计为 5；并发成交不能超过原报价量。
- 跨 RFQ、跨 Inquiry、跨 Quotation 的行 ID 请求全部返回 400/409，并且事务中没有半写入。
- 件号相同但 rfqLineId 不同的两行仍按 ID 隔离；不能用 partNumber 作为唯一键。
- 价格四舍五入、成本、毛利、税费和币种分组对账通过；任何客户端伪造 totalPrice 或 quantity 都以服务端行事实为准。

本设计保留了当前单行产品的可运行路径，同时把“部分报价、部分成交、部分出库”所需的四段 ID 链路固定下来。真正开启多行写入前，必须完成 M0 的历史关联报告和浏览器/API 回归。
