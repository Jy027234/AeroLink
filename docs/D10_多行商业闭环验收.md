# D10 多行商业闭环验收

日期：2026-09-08。范围依据已确认的自有库存销售、背靠背采购转售、USD、金额分级审批、默认禁止自批；本次没有扩大为交换件、寄售或外部 ERP 写入。

## 已实现的行为

- RFQ 支持 1–100 条明确需求行，服务端生成行 ID/行号。现代请求不能混用旧头部需求事实；新单行现代请求也保留 `lineItemsMode=true`。已有询价或报价引用的行不能被普通编辑改写或删除。
- 询价草稿必须携带选定的需求行。三行需求可以只选择其中两行；仍为草稿，不代表已向供应商发送。
- 报价支持选择需求子集，逐行数量、售价、成本和来源快照。供应商报价必须属于具体 RFQ 行；旧空关联仅在需求唯一行时兼容，不按件号猜测。
- 审批按整张报价 Decimal 合计执行 5,000/50,000 USD 分级，禁止自批，AOG 不绕过政策。快照覆盖头部条款及全部报价行；后续成交计数和状态变化不会使原审批失效。
- 客户接受必须提交当前版本及具体报价行/数量。每次接受生成独立订单、订单行和本次成交合同。报价行余量及同一需求在替代报价下的已成交量都受事务校验。
- 订单原有单报价唯一约束改为旧模式局部唯一索引；现代报价可生成多个分批订单。旧整单创建仍使用原有幂等流程。
- 列表、详情、操作和重放响应中的行成本及审批快照执行原有权限投影。PDF 展示全部报价行，订单合同只展示该订单的成交行。
- 历史回填明确跳过现代记录，不从兼容头字段制造新行；新旧对账分别执行各自事实规则。订单唯一性预检也区分旧模式和现代分批成交。
- 交易模式保持一致：旧标量报价不能针对逐行需求创建，逐行报价要求逐行需求；已有旧报价的需求不能再切换模式，避免混用两套成交数量规则。尚未报价的旧需求可先保存为逐行需求。
- 次行件号可用于搜索，报价及订单列表明确返回模式和全部行；CSV 保留每张单据一行，并附独立行明细 JSON。旧商品标量合同模板不能用于现代分批订单，必须使用明细表模板。
- 同一库存被多条报价行引用时，创建与审批均检查合计数量。审批校验毛利比例和供应商来源外键的一致性；需求完成保留已取消行，报价撤回使用数据库允许的行终态。

## 已取得的真实环境证据

1. Node 22.23.2、Prisma 5.22.0，隔离 PostgreSQL 16 库应用全部 22 条迁移。未修改原 review 库或生产数据。
2. `checkMultilineCommercialIntegration.ts` 实际创建 3 条需求、2 条报价，报价合计 `10000.3706`，经理超额和自批被拒绝，财务审批通过。
3. 第一次接受第一行 1 件，订单总额 `1000.0001`；第二次接受第一行 3 件、第二行 3 件，订单总额 `9000.3705`。两个订单合计精确等于原报价，报价行累计成交量为 `[4, 3]`。
4. 第一份合同 HTML 包含第一行件号，不含尚未成交的第二行。两次成交生成不同订单和合同 ID。
5. 陈旧版本、超出报价行余量、替代报价重复成交均回滚；部分成交后不能重置整单审批。两个并发请求争用同一版本时仅一方提交，订单及成交量仅增加一次。
6. Playwright `multiline-commercial-flow.spec.ts` HTTP 全链路通过，另覆盖严格请求校验、销售行成本隐藏、幂等请求重放、详情关联和实际 PDF 生成。
7. 在只含现代样本的第二个隔离库独立只读对账：1 个 RFQ / 3 条需求行、3 个报价 / 5 条报价行、3 个订单 / 4 条订单行，`PASS`、0 阻断、0 待核。金额 shadow 对账 6 记录 / 12 字段全部一致。
8. 回填只读预检跳过上述 1 个现代 RFQ、3 个现代报价、3 个现代订单，计划新增行数均为 0。没有执行历史数据回填。
9. 在独立临时输出目录完整生成 Prisma Client；与工作区的 DMMF 完全一致，查询引擎 SHA-256 一致。避免替换仍被其他本机进程占用的引擎文件，未停止来源不明的服务。
10. 浏览器真实操作从三行需求选两行、逐行定价、查看 USD 800.00 合计、保存草稿并提交审批通过。实际 PostgreSQL 撤回测试验证行状态约束，需求完成后取消行仍为 `CANCELLED`；这两个终态测试事务在断言后回滚。

## 本批次边界与下一步

- 本次完成商业行到分批订单的链路。现代订单尚未开放旧整单库存预留、质量审核或出库入口；这些入口会明确拒绝，需要 D12/D13 的逐行 Allocation、实物证据和分批发运模型。
- D11 商业版次、变更重审、历史有效期人工核对仍待完成。本批次不延长任何历史报价有效期。
- D14 采购单、收货/直发与结算摘要，D15/D16 服务端助手，以及生产镜像/恢复验收仍按原待办继续。该记录不代表产品已满足 M2/M3 上线门槛。
- 所有验收使用合成数据，没有向真实客户或供应商发送邮件，没有推送代码或部署生产。

## 重复执行

真实数据库脚本只允许显式 `AEROLINK_MULTILINE_INTEGRATION=true` 且本地数据库名称匹配 `aerolink_multiline_test_*`。先应用迁移，再在 server 目录使用 Node 22 执行：

```powershell
node --import tsx src/scripts/checkMultilineCommercialIntegration.ts
node --import tsx src/scripts/checkTransactionLineReconciliation.ts
node --import tsx src/scripts/backfillTransactionLines.ts
node --import tsx src/scripts/checkOrderUniqueness.ts
node --import tsx src/scripts/checkMoneyReconciliation.ts
```

HTTP 验收使用现有 seed 与显式测试密码，在独立端口运行：

```powershell
npx playwright test e2e/multiline-commercial-flow.spec.ts
```
